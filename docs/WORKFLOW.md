# Як працювати над EasyWAR

Правила для власника, Claude (у проєкті Claude і в Claude Code) та Codex. Невід'ємна
частина — [`../AGENTS.md`](../AGENTS.md): правила репозиторію, legacy HTML, перевірки.
Контекст проєкту — [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md), черга робіт —
[`BACKLOG.md`](BACKLOG.md).

## 1. Ролі й канали

| Хто | Що робить | Що не робить |
|---|---|---|
| Власник | ставить задачі, приймає рішення (архітектура, безпека, випуск), зливає PR у `main`, публікує чернетки випусків | — |
| Claude у проєкті Claude (чат, телефон) | пояснює код і документи, готує рішення, тексти, плани, перевіряє ідеї | не змінює репозиторій: якщо потрібні зміни коду — формулює задачу для Claude Code |
| Claude Code (хмарна сесія з репозиторієм) | виконує задачі в гілці `claude/<тема>`, запускає перевірки, комітить і відправляє гілку | не створює PR без прохання, не публікує випуски, не змінює `main` напряму |
| Codex | те саме, за `AGENTS.md` і власною дошкою задач | — |

Усі канали читають одні й ті самі файли: `PROJECT_CONTEXT.md`, `WORKFLOW.md`,
`BACKLOG.md`, `AGENTS.md`, аудит.

## 2. Як ставити задачу

Достатньо чотирьох речей; решту агент бере з умовчань нижче.

1. **Де:** модуль або екран (ПС, РВ, Артилерія, ПВК, УДШВ, стартовий екран, телефон,
   Signal, резервні копії, оновлення, ядро/база).
2. **Що зараз і що має бути:** поведінка «до» і «після» словами користувача; якщо є
   скриншот або приклад з синтетичними даними — додати.
3. **Межі:** чого не чіпати (наприклад, «таблицю не переформатовувати», «без нової
   міграції», «лише ПС»).
4. **Як перевірити:** що має побачити власник після злиття.

Приклади:

```text
ПВК, вкладка «Наші втрати»: фільтр за підрозділом губиться після перемикання періоду.
Має зберігатися до перезавантаження. Таблицю й SQLite не чіпати. Перевірка: обрати
підрозділ, змінити період — фільтр лишається.

Артилерія, «Внесення»: додати поле «Примітка» (до 200 символів) до рядка підрозділу;
пишеться в існуючий стовпець K аркуша «Зведення». Формули й злиття не чіпати.
Тест на запис у синтетичну таблицю.
```

Якщо задача з беклогу — досить назвати її номер (`P1-3`) і уточнення, якщо є.

### Умовчання, коли в задачі не сказано інакше

- Мова всього, що бачить користувач, — українська; код і коментарі в коді — англійська.
- Нова логіка — у `*-core.js` з тестом; UI — окремо. У Rust — у відповідному модулі з
  `#[cfg(test)]`.
- Legacy-сторінки правляться точково (`AGENTS.md`), а не переносяться в модулі, якщо
  задача не про міграцію.
- Нова можливість вимкнена за замовчуванням, якщо вона виходить у мережу або змінює
  файли користувача.
- Зміни в інтерфейсі супроводжуються абзацом у `USER_GUIDE.md`.
- Схема бази не змінюється, якщо задача цього прямо не вимагає; якщо вимагає — нова
  міграція, тест, `DATABASE.md`.
- Версія не підвищується; це окрема дія «Випуск».
- Уточнення в агента одне, на початку, і лише якщо від відповіді залежить суттєво
  інша реалізація. Інакше — робить і пише у звіті, яке тлумачення обрав.

## 3. Цикл задачі

1. Прочитати `CLAUDE.md`/`AGENTS.md`, знайти задачу в `BACKLOG.md`, подивитися
   відповідний розділ документації.
2. Гілка `claude/<коротка-тема>` від актуального `origin/main`.
3. Зміни малими кроками; кожен крок — зі своєю перевіркою.
4. Перевірки шару (розділ 5). Жодного «готово» без них.
5. Документація разом із кодом (розділ 7).
6. Коміт(и) українською, `git push -u origin <гілка>`.
7. Звіт власнику (розділ 9). Власник відкриває PR (або просить агента), зливає.
8. Після злиття: закрити пункт у `BACKLOG.md`, оновити файли проєкту Claude, якщо
   змінилися правила чи контекст.

## 4. Гілки, коміти, PR

- `main` — захищена домовленістю: лише через PR; прямих пушів немає.
- Назви гілок: `claude/<тема>` (наприклад `claude/pvk-losses-filter`), для Codex —
  за його правилами.
- Повідомлення коміту: перший рядок «Модуль: що зроблено» до ~100 символів, далі за
  потреби абзац «чому» і «як перевірено». Приклади з історії:
  `Артилерія: іконки боєприпасів за калібрами у зведенні, на вкладці «Боєприпаси» та у формі внесення`,
  `Випуск 1.0.7: боєприпаси матрицею, довідник боєприпасів Артилерії, емблеми й іконки`.
- У коміт не потрапляють: `dist/`, `node_modules/`, `target/`, таблиці `.xlsx` (крім
  порожніх базових і синтетичних фікстур, явно дозволених у `.gitignore`), бази,
  логи, резервні копії, згенеровані фікстури.
- Великі бінарні файли (моделі `.glb`, зображення) — лише коли справді потрібні, і
  не перекомічувати ітерації: кожна версія назавжди лишається в історії (беклог P2-6).
- Історію не переписувати (`rebase`, `amend`, `force-push`) на спільних гілках.

## 5. Перевірки за шарами

| Змінено | Обов'язково виконати |
|---|---|
| `src/*.js`, `src/public/*.js`, `tests/` | `npm run test:unit` |
| `src/*.html` (legacy) | правила «Legacy HTML editing» в `AGENTS.md`; синтаксис кожного inline-скрипта; `npm run test:unit` (`desktop-frontend`, `module-editor`, `pwa-viewer`) ; `npm run build` |
| `src-tauri/src/**` | `cargo test`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo fmt --check` (з `--manifest-path src-tauri/Cargo.toml`) |
| `src-tauri/migrations/` | усе з попереднього рядка + тест міграції + `DATABASE.md` + `migrations/README.md` |
| `vite.config.js`, `script/build_standalone.mjs`, `package.json` | `npm run build`, `npm run test:unit` (`standalone-build`, `pwa-viewer`) |
| `.github/workflows/`, `script/*release*`, `tauri*.conf.json` | `node script/release_version.mjs`, `tests/release.test.mjs` |
| Будь-що з UI | ручна перевірка в запущеному застосунку, де можливо (локально `npm run tauri dev`; у хмарі — скіл `run-easywar` зі скриншотами) |

CI (`desktop-build.yml`) виконує лише `test:unit` і `build` на Linux; Rust-перевірки,
macOS і Windows — відповідальність того, хто змінює. Коли CI доповнять (беклог P1-1),
цей розділ оновити.

Нестабільні тести не вимикати й не «ігнорувати»: або чинити, або заводити пункт у
беклог із посиланням на падіння.

## 6. Дані й безпека

- Тільки синтетичні дані: `tests/fixtures/`, `.claude/skills/run-easywar/fixtures.py`
  (генерує таблиці з вигаданими назвами й координатами), порожні базові таблиці.
- Якщо для відтворення помилки потрібна структура реальної таблиці — описати
  заголовки й формат значень словами або зробити анонімізовану копію локально і не
  передавати її в чат, репозиторій чи проєкт Claude.
- Секрети (ключі підпису, токени, ключ Planet, паролі) не з'являються в коді,
  документах, чатах, скриншотах; у CI — лише через GitHub Secrets.
- Будь-яка нова мережева взаємодія або зміна `capabilities`, CSP, оновлювача,
  Signal-політики — окреме рішення власника, зафіксоване в задачі.
- Знайдена вразливість — спершу пункт у `BACKLOG.md` з посиланням на аудит, потім
  виправлення окремою гілкою.

## 7. Документація разом із кодом

| Зміна | Оновити |
|---|---|
| Поведінка або вигляд для користувача | `USER_GUIDE.md` (відповідний розділ) |
| Структура фронтенду, редактор модуля, нові сторінки | `UNIFIED_FRONTEND.md`, `README.md` (layout) |
| Міграція, репозиторій, профілі | `DATABASE.md`, `src-tauri/migrations/README.md` |
| Signal, XLSX, аналітика, телефон, презентації | відповідний `docs/*.md` |
| Випуск | `docs/releases/vX.Y.Z.md` |
| Правила роботи | `WORKFLOW.md`, `AGENTS.md`, `CLAUDE.md`, `PROJECT_INSTRUCTIONS.md` |
| Стан проєкту, нові модулі, словник | `PROJECT_CONTEXT.md` |
| Закрита або нова робота | `BACKLOG.md` |

Після зміни файлів із останніх трьох рядків — перезавантажити їх у проєкт Claude.

## 8. Випуск версії

1. Переконатися, що в `main` зелені всі перевірки розділу 5 (включно з Rust).
2. Підняти версію в п'яти файлах: `package.json`, `package-lock.json`,
   `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`;
   `node script/release_version.mjs` має сказати «версії узгоджені».
3. Написати `docs/releases/vX.Y.Z.md` мовою користувача: що нового, що змінилося в
   даних (міграції чи «схема бази не змінюється»), відомі обмеження.
4. Коміт «Випуск X.Y.Z: …», PR, злиття в `main`.
5. Тег `vX.Y.Z` на коміт злиття, `git push origin vX.Y.Z`. CI збирає macOS і
   Windows, перевіряє підписи, створює **чернетку** в `easywar-releases`.
6. Перед публікацією: встановити з чернетки поверх копії зі старою синтетичною
   базою, переконатися, що дані, налаштування й запуск збережено.
7. Записати рішення про публікацію технічного випуску (хто, ризик, строк,
   відкочування) — у `docs/releases/DECISIONS.md` (беклог P1-6), і лише тоді
   опублікувати чернетку.
8. Не більше одного випуску на день без вагомої причини: кожне оновлення — 127–259 МБ
   на кожну встановлену копію.

Деталі механізму — `UPDATES.md`; повний шлюз production — `RELEASE_CHECKLIST.md`.

## 9. Звіт про статус

Коротко, без переказу коду:

```text
Змінено: ПВК «Наші втрати» — фільтр підрозділу зберігається в стані вкладки
(src/own-losses-dashboard.js, src/own-losses-dashboard-core.js); тест у
tests/own-losses-dashboard.test.mjs.
Перевірено: npm run test:unit — 327/327; npm run build — ок; скриншот у run-easywar.
Не перевірено: macOS/Windows (сесія Linux).
Далі: PR з гілки claude/pvk-losses-filter; беклог не зачеплено.
```

## 10. Підтримка цих правил

- Правила змінює власник; агенти пропонують зміни окремим комітом із поясненням.
- Раз на випуск: `PROJECT_CONTEXT.md` називає актуальну версію й стан модулів,
  `BACKLOG.md` не містить закритих пунктів без позначки, `README.md` не суперечить.
