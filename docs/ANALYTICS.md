# Локальна аналітична модель EasyWAR

## Межа джерела

Команда Tauri `get_dashboard_model` формує read-only модель дашборда з локальної
SQLite. Єдиним джерелом є останній immutable `revision_history.snapshot_json`
для кожного звіту, чий поточний стан і останнє рішення дорівнюють `APPROVED`.

Модель не читає й не повертає:

- `raw_sources.raw_text` або `raw_payload_json`;
- проміжні `parsed_report_versions`;
- ручні виправлення як окремі події;
- звіти зі станом `NEW`, `PARSED`, `NEEDS_REVIEW` або `REJECTED`;
- локальні report/source/revision ID, хеші, рецензентів чи аудит.

Ручні виправлення враховуються лише через уже матеріалізований та схвалений
знімок ревізії. Порожня база схвалених записів повертає коректну порожню модель,
а не помилку чи підстановку даних із XLSX.

## Контракт версії 1

Верхній рівень відповіді містить:

- `schemaVersion: 1`;
- `source: "approved_sqlite_revisions"`;
- кількість схвалених звітів, усіх нормалізованих записів джерела та записів у
  поточній вибірці;
- повний доступний діапазон дат і діапазон дат поточної вибірки;
- застосований період та кількість виключених записів, зокрема без валідної дати;
- кількість записів із базовими проблемами якості та загальну кількість проблем;
- масив `records`.

Кожен запис зберігає схвалені значення, потрібні майбутньому дашборду: номер,
дату й час, цілі, підрозділ, район, координати, типи цілей, тип ЛА, боєприпас,
кількість, результат, ознаку відбою, причину та примітку. Разом із сирими
схваленими значеннями дати/кількості повертаються нормалізовані значення та
машинні коди базових проблем якості.

Нормалізація повторює перевірені правила legacy-дашборда для:

- ISO, `дд.мм.рррр`, `дд/мм/рррр` і XLSX serial date;
- категорій результату `hit`, `partial`, `miss`, `unknown`;
- ознаки `відбій` у результаті або причині;
- числового префікса кількості боєприпасів;
- списків номерів і типів цілей;
- пробілів у назві підрозділу, префікса `н.п.` і маркерів порожнього боєприпасу.

Некоректна версія знімка, не-масив `records`, порожній або більший за 64 масив,
чи поле несподіваного JSON-типу зупиняють побудову без відображення значення в
тексті помилки. Загальна відповідь обмежена 100000 записами.

## Фільтр періоду

Команда приймає необов’язковий аргумент `period`:

```javascript
invoke('get_dashboard_model', {
  period: { from: '2026-01-01', to: '2026-01-31' },
});
```

Межі включні та незалежні: можна передати лише `from` або лише `to`. Порожні
межі еквівалентні відсутній межі. Непорожня межа має бути реальною календарною
датою у канонічному форматі `РРРР-ММ-ДД`, а `from` не може бути пізніше за
`to`. Невідомі поля аргументу відхиляються.

Без активних меж модель повертає всі схвалені записи, включно із записами з
некоректною датою для подання якості. Коли хоча б одна межа активна, записи без
нормалізованої дати не входять до вибірки та обліковуються в
`period.excludedUndatedRecords`. `availableDateRange` завжди описує все джерело,
а `dateRange` — лише записи, що пройшли фільтр. Порядок схвалених записів не
змінюється.

## Що ще не реалізовано

Джерельна модель і Tauri-команда вже підтримують фільтри періоду. Вбудований
legacy-дашборд поки продовжує працювати з відкритим користувачем XLSX. Наступні
окремі пункти ROADMAP мають додати формули ефективності, розрізи, розширене
подання якості, абстракцію карти, експорт views і явне перемикання UI на
SQLite-модель.

Синтетичні тести перевіряють нормалізацію, порожню модель, fail-closed JSON та
повний in-memory SQLite-ланцюжок із одночасними `APPROVED` і `REJECTED`
ревізіями, включні й відкриті межі періоду, виключення записів без дати та
відмову для некоректних діапазонів. У серіалізованій моделі немає
raw/parsed/rejected вмісту або внутрішніх ідентифікаторів.
