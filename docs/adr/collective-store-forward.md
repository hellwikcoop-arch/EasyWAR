# ADR: тимчасове зберігання зашифрованих пакетів (store-and-forward)

**Статус:** Запропоновано (21.10.2026). Не затверджено власником. Реалізацію не дозволено.  
**Етапи:** C4 (Base44-mailbox, класи A–C), C6c (LAN, якщо JE-20), C8 (WAN, лабораторія).  
**Пов'язане:** [`COLLECTIVES_PLAN.md`](../COLLECTIVES_PLAN.md) §3 («не губити єдину копію»),
§4, §12 (Base44 у beta); рев'ю J3, розділ 3.

## Контекст

Коли відправник і одержувач не онлайн одночасно, LAN-обмін зупиняється. Для класів A–C це
вирішує Base44 (C4), для класу D у v1 — ні (К8).

## Рішення (пропоноване)

1. Один контракт для всіх сховищ (Base44-mailbox, вузол у LAN, майбутній WAN-вузол), щоб
   транспорт замінювався без зміни формату операцій:
   `put(envelope, recipient, expiry, size_limit) → stored_receipt`;
   `fetch(recipient, cursor, page_limit) → envelopes + next_cursor`;
   `ack(recipient, envelope_id, verification_receipt) → ack_status`.
2. Ключ унікальності `(recipient_scope, envelope_id, digest)`. Переповнення — чесне
   `REJECTED_CAPACITY`; відправник не видаляє свою копію за невідомою квитанцією.
3. Зберігається **лише шифротекст** і мінімум службових полів (К4). `STORED` підписане вузлом і
   не означає `APPLIED`.
4. Роль STORE_FORWARD на комп'ютері учасника — **окрема** явна згода від RELAY, з квотою диска,
   TTL і показом обсягу; за замовчуванням вимкнено. Лабораторні параметри J5 (до 100 МБ, TTL до
   24 год) — лише для синтетичного прототипу; остаточні — JE-10 після вимірювань.
5. Для класу D — лише вузол у LAN; чи дозволено — JE-19.
6. Після вимкнення ролі нові `put` відхиляються; наявні пакети доставляються до TTL або
   очищуються за підтвердженням власника комп'ютера. Уже передане іншим не відкликається.

## Альтернативи

Лише Base44 для асинхронності (клас D тоді працює тільки онлайн у LAN). Чи потрібен C6c у v1 —
JE-20.

## Відкрите для власника

JE-10, JE-19, JE-20 (рев'ю J3, розділ 5).

## Перевірки (лише синтетичні)

M02, M06, S06; квота, TTL, перезапуск вузла, втрата квитанції, `REJECTED_CAPACITY`.

## Ізольований зріз 29.10.2026: локальна черга конвертів

На запит JE підготовлено `src-tauri/src/collective/relay.rs` як тестований offline
data-plane для `EnvelopeV1`. Він зберігає лише готові зашифровані конверти з
відкритими полями заголовка, переживає перезапуск, дає сторінкове читання за
`recipient_scope`, обмежує розмір, загальну квоту й TTL до 24 годин та відхиляє
повторний `envelope_id` з іншим digest. Запис снапшота виконується через тимчасовий
файл і заміну. Помилка до заміни не змінює попередній стан.
Окремий OS file lock відхиляє друге одночасне відкриття тієї самої черги;
після закриття власника чергу можна знову відкрити без втрати пакетів.
Це локальний результат `Stored`/`AlreadyStored`, **не** підписана квитанція вузла
і **не** свідчення застосування на пристрої одержувача.

Модуль не підключено до IPC, мережі, UI чи автоматичної відправки. Він не має
`ack`: видалення за неперевіреною квитанцією могло б втратити єдину копію;
конверт залишається до TTL. Немає автентифікації запитувача та перевірки членства.
Клас C/D міститься всередині ciphertext, тому relay не може його перевірити.
Перед будь-яким WAN-send потрібні авторитетні Rust-перевірки класу C після факту,
підтвердженого членства, права запису, згоди користувача і прийнятого E2EE
транспорту безпосередньо перед відправкою. Клас D залишається тільки в LAN.
Незалежні безпекові gates, вибір relay і JE-10/JE-19/JE-20 лишаються відкритими.

## Зріз 29.10.2026 (ніч): автентифікація запитувача й перевірене підтвердження

`src-tauri/src/collective/relay_auth.rs`, `AuthenticatedRelay` — обгортка над `OfflineMailbox`
для одного колективу, що реалізує контракт п. 1–3 без сокетів і IPC:

- **Автентифікація.** Кожен `put`/`fetch`/`ack` підписаний Ed25519-ключем пристрою учасника:
  `мітка ‖ collective_id ‖ member_id ‖ device_pub ‖ issued_at ‖ nonce₁₆ ‖ тіло` (мітки
  `easywar/collective/v1/relay-put|relay-fetch|relay-ack`). Вузол приймає лише пристрій,
  підтверджений на поточному журналі складу, від невідкликаного учасника; `issued_at` — у межах
  300 с від годинника вузла; `nonce` не повторюється (кеш до 4096 номерів, номер записується лише
  після перевірки підпису й членства; повний кеш — `Busy`, а не витіснення).
- **Адресат.** `recipient_scope` = нулі — увесь колектив, читає будь-який активний учасник;
  `member_scope = SHA-256("easywar/collective/v1/member-scope" ‖ collective_id ‖ member_id)[..16]` —
  один учасник, читає й підтверджує лише він (`ScopeForbidden` для інших). Це конкретизує
  «непрозорий ID» з `collective-crypto.md`, 2.4: сторонній без `member_id` адресу не пов'яже.
- **Квитанція `STORED`** підписана ключем вузла: `relay_pub ‖ collective_id ‖ scope ‖ envelope_id ‖
  digest ‖ expires_at ‖ stored_at ‖ already_stored`. Відправник перевіряє її ключем вузла, якому
  довіряє, і digest свого пакета; чужа чи підроблена — пакет у відправника не видаляється.
- **ACK.** Адресат підписує `scope ‖ envelope_id ‖ digest` після того, як `receive` дав `Apply` чи
  `Idempotent`. Пакет учасника видаляється лише за таким підтвердженням із тим самим digest
  (`OfflineMailbox::remove`; інший digest — відмова без видалення). Пакет усього колективу
  підтвердженням не видаляється (`Retained`): інші ще не прочитали, він лежить до TTL.

Не зроблено: шифрування каналу (TLS/Noise — разом із транспортом), вибір і довіра до вузла
(список `relay_pub` у налаштуваннях колективу), роль STORE_FORWARD зі згодою власника комп'ютера,
збереження кешу номерів між запусками, JE-10/JE-19/JE-20.
