# ADR: криптопрофіль і ідентичність колективу

**Статус:** **Реалізовано в C2 (варіант Б), у `main` з 29.10.2026 (PR #180); gate G12 закрито з умовами**
(рішення JE-T5 від 29.10.2026 на коміті `70bade5`, умови J5 — нижче й у чеклісті G12). Рішення власника 29.10.2026
(JE, контроль J5; журнал `easywar-staff/tasks/T-0016/je-decision-R3.md`): JE-15 — варіант Б, умовно
(`ed25519-dalek 2.2`, `x25519-dalek 2.0`; `spake2 0.4` — лише з C2p; без переходу на покоління 0.11;
обов'язкова незалежна перевірка протоколу обгортки ключів і векторів перед production —
розділ 5, G12); JE-16 — варіант а (`expiry` лише всередині payload); JE-18 — варіант Ф (файл +
Argon2id, ADR P1). Код C2 (наказ T-0017, R4): модуль `src-tauri/src/collective/` (`identity`,
`epoch`, `envelope`, `codec`, `replay`, `secret_store`) без команд Tauri, без мережі й міграцій;

і `tests/collective-crypto-vectors.test.mjs` (незалежна перевірка `node:crypto`). Фактична зміна

## 2. Контракт (пропонований; набуває чинності після JE-15/16/18)

### 2.1. Версія протоколу

`protocol_version = 1` (u16). Пакет з іншою версією відхиляється без спроби розшифрування;
перехід на версію 2 — новий ADR. Ідентифікатор набору: `suite = 1` = Ed25519 + X25519 +
HKDF-SHA256 + XChaCha20-Poly1305 + Argon2id (для сховища). Інший `suite` → відмова.

### 2.2. Ідентичність

- **Ключ учасника** (на профіль у колективі): Ed25519 для підпису + X25519 для обгорток
  (окрема пара, не виведена з Ed25519). ID учасника = SHA-256(`"easywar/collective/v1/member-id"`
  ‖ публічний ключ підпису), 32 байти; у інтерфейсі — перші 10 символів base32. Не виводиться
  з MAC/IMEI/серійних номерів і **не використовується** як ідентифікатор лічильника К11.
- **Зв'язування ключа обміну з колективом** (G12, U1): запис `{sign_pub, exchange_pub, collective_id,
  issued_at}` під підписом Ed25519 учасника над `"easywar/collective/v1/exchange-binding" ‖ member_id ‖
  exchange_pub ‖ collective_id ‖ issued_at` (окрема мітка, не збігається з міткою запису пристрою).
  Перевірений запис — єдиний шлях до учасника, якому можна видати обгортку (`BoundMember`, U2): журнал
  складу приймає вступ лише з ним, повторний вступ ключ обміну не перезаписує, ротація — окремий запис
  журналу з новішим (`issued_at` строго більший) записом того самого учасника; відкликаний учасник ні
  обгорток, ні ротації не отримує.
- **Ключ пристрою**: Ed25519, запис `{device_pub, member_id, issued_at}` підписаний ключем
  учасника; операції підписує пристрій; одержувач перевіряє ланцюжок пристрій → учасник →
  підписаний журнал складу (C1c).
- Ключі «Офісу» і ключі колективу розділені мітками HKDF: `easywar/library/v1/*` проти
  `easywar/collective/v1/*`; спільний майстер-секрет між ними не існує.

### 2.3. Ключ колективу й епохи

- Ключ епохи: 32 випадкові байти з OS CSPRNG; `epoch` — u32, зростає на 1 при кожному
  відкликанні; епоха 0 — створення колективу.
- **Обгортка епохи для учасника** (варіант Б, формат після U3): `shared = X25519(eph_priv, member_x25519_pub)`;
  `kek = HKDF-SHA256(ikm = shared, salt = collective_id ‖ epoch, info = "easywar/collective/v1/epoch-wrap" ‖
  eph_pub ‖ member_x25519_pub)`; `wrapped = XChaCha20-Poly1305(kek, nonce₂₄, epoch_key, aad = header)`;
  відкритий заголовок обгортки (у такому порядку, увесь в AAD): `v` (u16, =1), `suite` (u16, =1),
  `collective_id`, `epoch`, `member_id`, `eph_pub`, `nonce` — 112 байтів; інші `v`/`suite` відхиляються
  до розгортання. Обгортка створюється лише для учасника з перевіреним зв'язуванням (2.2), неконтрибутивний
  спільний секрет — відмова (`WeakExchangeKey`). Ефемерний ключ одноразовий, затирається.
  Варіант А: HPKE base mode `DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20Poly1305`
  (RFC 9180) з тією самою `info` і AAD.
- Новий учасник (К3) отримує обгортки всіх епох; відкликаний не отримує нової епохи.

### 2.4. Конверт операції (`EnvelopeV1`)

Відкриті поля — **лише** (К4, AC24, JE-16): `v` (=1), `suite` (=1), `collective_id`
(16 випадкових байтів), `envelope_id` (16 випадкових байтів), `epoch` (u32), `nonce` (24 байти),
`recipient_scope` (16 байтів, непрозорий випадковий ID або нулі для всього колективу).
**Немає** `class_hint`, автора, назви таблиці, часу, лічильників. Усе інше — всередині ciphertext.

- **AAD = канонічне кодування всіх відкритих полів** у сталому порядку (розділ 3): підміна
  будь-якого відкритого поля ламає тег.
- **Payload** (усередині): `{op (C1b, повний рядок), author_member_id, device_pub, client_time,
  class, table_id, op_id, membership_seq, expiry?}` + підпис Ed25519 пристрою над канонічним
  кодуванням payload з префіксом `"easywar/collective/v1/op"`. `membership_seq` — номер останнього
  запису підписаного журналу складу (C1c), який автор бачив під час створення операції;
  `client_time` — лише довідкове поле для журналу змін (К1), **не критерій авторизації**. Клас перевіряється одержувачем **усередині**
  розшифрованого payload (C06); дозволеність транспорту відправник бере з локальної політики
  (`networkPolicy` → `routeFor`).
- **`expiry` — варіанти для JE-16:** (а) лише всередині ciphertext, TTL сховища задає вузол
  (рекомендація J3); (б) відкрите поле з грубою точністю (доба) — дозволяє сховищу видаляти
  протерміноване без ключа, але видає ритм роботи; (в) без `expiry` взагалі, лише TTL вузла.
- **Nonce:** 24 байти з OS CSPRNG на кожен конверт і кожну обгортку; лічильники не
  використовуються; ключ епохи змінюється при відкликанні, окремого ліміту на кількість
  конвертів для 192-бітного nonce не потрібно.
- **Дедуплікація й anti-replay — два рівні (зауваження J5 C2a-01):**
  1. *Транспортний конверт.* Журнал `(collective_id, envelope_id)`: той самий `envelope_id`
     вдруге — мовчки пропускається (повторна доставка тим самим чи іншим шляхом). Інший
     `envelope_id` з тим самим payload — нормальний випадок **повторного шифрування** (новий
     nonce, інша епоха після ротації, інший transport): ciphertext інший, і це не порушення.
  2. *Логічна операція.* Журнал `(collective_id, author_member_id, op_id) → op_digest` (G12, A6:
     однаковий `op_id` від різних авторів — різні операції), де
     `op_digest = SHA-256(канонічне кодування підписаного payload без поля підпису)` — не
     залежить від nonce, епохи й шляху доставки. Той самий `op_id` з тим самим `op_digest` —
     ідемпотентно пропускається (уже застосовано); той самий `op_id` з іншим `op_digest` —
     `integrity_violation`, відхиляється й записується (правило C1b про дублікати). Підпис
     перевіряється до порівняння digest, тож підмінити payload під чужий `op_id` без ключа
     пристрою не можна.
  Невідома епоха — відхилення без спроби розшифрування.
- **Відкликання й довіра до часу (зауваження J5 C2a-02):** `client_time` контролює автор, тому
  авторизація операції визначається лише **автентифікованим журналом складу** (C1c, підписані
  записи запрошення/згоди/відкликання з номерами `seq`) і епохою:
  1. ланцюжок пристрій → учасник дійсний: запис пристрою підписаний ключем учасника й не
     відкликаний на момент `membership_seq`;
  2. учасник має право запису на таблицю за станом журналу складу на `membership_seq`;
  3. `membership_seq` не більший за `latest_seq` одержувача — **суцільний застосований префікс**
     журналу складу (G12, A3: запис після розриву не враховується, доки розрив не заповниться;
     недійсний запис зупиняє префікс). Операція «з майбутнього» журналу відкладається до
     отримання журналу, не застосовується, і лише в межах (G12, N1): горизонт `membership_seq −
     latest_seq ≤ 1024`, обмежена черга відкладених конвертів (попередньо 256 конвертів, TTL 7 діб,
     повна черга — відмова без витіснення), а автор, відкликаний уже на поточному журналі, не
     відкладається — `MemberRevoked` одразу;
  4. `epoch` конверта — епоха, яку автор законно мав на `membership_seq` (після відкликання
     автор не має нової епохи, тож операція під новою епохою від нього неможлива без ключа).
  *Операції, створені офлайн до відкликання й доставлені після нього* (умови 1–4 виконані,
  але на поточному `seq` автор уже відкликаний) — правило для JE (**C2a-02, підпитання
  JE-16**): (б) **відхиляти** всі операції відкликаного після запису відкликання, автор при
  потребі повторно додається (К3) — рекомендація J3 для v1 і обов'язково для класу D; (а)
  приймати лише в карантин «від відкликаного учасника, до відкликання» з ручним рішенням
  адміністратора (C1d, OwnerDecisionRequired). `client_time`, раніший за відкликання, сам по
  собі нічого не дозволяє.
  Негативні вектори (розділ 4): «backdated signed operation» (`client_time` до відкликання,
  `membership_seq` після — відхилити), «старий конверт після відкликання» (`membership_seq` до
  відкликання, доставлено після — (б) відхилити / (а) карантин), «операція з `membership_seq`
  з майбутнього» (відкласти).
- **Помилки:** назовні один код «пакет відхилено» без байтів, адрес і причини; причина — лише
  в локальному журналі (`Denied`-подібний перелік без даних), як у `network_policy.rs`.

## 5. Security gate перед production C2 (зауваження J5 C2a-03)

`cargo audit` перевіряє лише відомі вразливості залежностей, **не конструкцію протоколу**.
Якщо JE обере варіант Б (власна обгортка X25519 → HKDF → XChaCha20-Poly1305 замість RFC 9180),
до злиття production-коду C2 обов'язковий окремий gate (пропозиція: **G12** у
`COLLECTIVES_PLAN.md` §9): незалежна рецензія дизайну протоколу (не автором коду; C3 з
чеклістом або зовнішній рецензент за рішенням JE) за пунктами: відповідність конструкції
обгортки HPKE-base (DHKEM-X25519 + HKDF-SHA256 + AEAD) і RFC 9180 A.2 як контрольних векторів;
межі nonce (192 біт, CSPRNG, ротація епохи); контекстні мітки HKDF (`easywar/collective/v1/*`,
відсутність перетину з `easywar/library/v1/*`); AAD = усі відкриті поля; two-level anti-replay
(розділ 2.4); правило відкликання; повний прогін векторів розділу 4 на Windows і macOS (G06).
Результат gate — запис у `docs/evidence/collectives/`. Варіант А цей gate не скасовує, лише
звужує до перевірки використання крейта `hpke` і контекстних міток.

**Фактичний allowlist залежностей для C2 (варіант Б):** `ed25519-dalek 2.2` (features
`rand_core`, `zeroize`), `x25519-dalek 2.0` (`static_secrets`, `zeroize`), `spake2 0.4` (C2p;
може бути відкладений до C2p окремим `cargo add`). `ciborium` **не вводиться**, якщо JE прийме
рекомендацію про власний codec (розділ 3); тоді зміна lock — 8 нових крейтів замість 13.
**Факт C2 (T-0017):** +7 крейтів (`spake2` відкладено до C2p, `ciborium` не введено, `zeroize`
вже був); `cargo audit --file src-tauri/Cargo.lock` з кореня (з `.cargo/audit.toml`) — 0 вразливостей,
3 дозволені попередження про непідтримувані крейти Tauri/Linux.

## Перевірки (лише синтетичні)

Вектори розділу 4; зміна байта шифротексту, заголовка чи підпису → відмова; невідома епоха;
пошкоджена обгортка; повторне шифрування тієї самої операції — ідемпотентно; той самий
`op_id` з іншим `op_digest` — `integrity_violation`; backdated signed operation і старий конверт
після відкликання — відхилення (чи карантин за (а)); `membership_seq` з майбутнього —
відкладення; G06, G11, G12 (розділ 5).
