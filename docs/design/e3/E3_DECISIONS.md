# E3-П: рішення JE, ризики й межі

**Статус:** рекомендації J5 для рішення власника. Позначка `requires_decision` означає, що Codex не надає дозволу на міграцію або реалізацію. Поточний пакет — лише документація.

## 1. Питання до JE

| ID / стан | Питання й альтернативи | Рекомендація для рішення JE | Наслідок |
|---|---|---|---|
| D1 `requires_decision` | Чи затвердити `e3_*` окремим append-only кандидатом `0017` після повторної перевірки main? Альтернатива — змінити `dashboard_module_fields`. | Окремі таблиці; не класти binding у поля модуля. | Без рішення не створювати міграцію. |
| D2 `requires_decision` | Як трактувати прив'язку XLSX при перейменуванні/переміщенні? Альтернативи: автоматично впізнавати за digest або явний relink. | Явний relink до того самого `sourceId` лише після перевірки профілю й користувача. | Уникнути випадкового злиття різних джерел з однаковими байтами. |
| D3 `requires_decision` | Який мінімальний перший вертикальний сценарій: тільки `linked_xlsx` чи водночас `module_sqlite`? | Почати з `linked_xlsx`, одна таблиця; SQLite-адаптер окремим кроком, але тип/схему передбачити зараз. | Не збільшувати ризик для старих модулів у першому запуску. |
| D4 `requires_decision` | Валідація `definitionId`/ролі у Rust для E1 Rust/v1/legacy: окремий ручний каталог, генерований manifest з E1, чи дозволити невідомі binding? | Генерований versioned manifest із `module-definition-core.js`/Rust-каталогу з тестом синхронізації; до нього non-Rust binding тільки preview/unsupported. | Не створити третій незалежний реєстр і не довіряти довільному JS-полю. |
| D5 `requires_decision` | Одиниці, null rule та агрегація: allowlist чи вільний текст? | Кодована одиниця/агрегація з явним підтвердженням; невідома одиниця зберігається як «не вирішено», без сум/конвертацій. | Потрібен UX вибору одиниці; DDL лише обмежує довжину, Rust — семантику. |
| D6 `requires_decision` | Чи зберігати у E3 персистентні ParsedRow/Value для офлайн-доступу без XLSX? Альтернативи: копія рядків або повторне локальне читання. | У E3 лише повторне читання прив'язаного локального XLSX; без дублювання клітинок. | Без файла source стає unavailable, але старі таблиці модулів лишаються. Окремий кеш — інший проєкт із provenance. |
| D7 `requires_decision` | Політика видалення E3 source/schema та історії. Альтернативи: cascade з профілем чи окреме архівування. | Для свідомого видалення всього профілю cascade E3 metadata; для звичайного «відв'язати» source позначати unavailable/stale, історію не стирати автоматично. | Потрібне окреме UI-рішення про залежності, без впливу на XLSX. |
| D8 `requires_decision` | Чи достатньо startup verified backup, чи вимагати ще видиму ручну копію перед E3 rollout? | Startup backup є технічним мінімумом; перед продуктивним rollout додаткова локальна копія з перевіркою, без мережі. | Врахувати місце на диску та UX відновлення. |
| D9 `requires_decision` | Як формувати `physical_fingerprint` і `sourceVersionToken` кросплатформно? | Канонічна UTF-8/JSON схема з версією алгоритму, SHA-256; фіксувати bytes/normalization у тестах Windows/macOS. | Зміна алгоритму потребує нової версії, а не тихого зіставлення. |
| D10 `requires_decision` | Чи дозволяти першому E3 позначати `ready` для `catalog-v1`/`legacy`, якщо адаптер візуалізації відсутній? | Ні: зберігати/показувати обґрунтовані рекомендації, але `unsupported` доки адаптер не доведено. | Зберігається повнота каталогу без фальшивої доступності. |

Прийняті попередні рішення з `MODULES_ROADMAP.md` (одне джерело для кількох майбутніх екземплярів, ручне підтвердження неоднозначностей, сирий XLSX не переписувати, schema профілю окремо від шаблону) тут **не відкриваються заново**. Рядки таблиці вище уточнюють деталі E3-П, які потребують JE.

## 2. Ризики з доказами й запобіжниками

| Ризик | Доказ у чинному репозиторії | Проєктний запобіжник |
|---|---|---|
| Втрата користувацьких назв/binding після оновлення Rust-шаблону | `dashboard_modules.rs::synchronize_template_schema()` видаляє й заново вставляє `dashboard_module_fields`. | Окремі `e3_profile_schema_versions`/`e3_column_bindings`; тест restart + catalog update. |
| Перетворення preview ID на постійний ключ | `dashboard-recommendation-core.js::profileSource()` за замовчуванням дає `preview/unversioned`; `module_source_selection.rs` TTL і session ownership. | Сталий `ds-<hex>` у SQLite; після commit перепрофілювати з Rust version token; preview recommendation тільки для огляду. |
| Втрата рядків/хибне `ready` на неповному читанні | `module_source.rs` пропускає порожні рядки, обмежує 10 000+50/200 і повертає `truncated`; JS має `rowCoverage`/`partial`. | Зберігати координати й `partial`, показувати прогалини, не виводити точні суми/`ready`. |
| Помилковий ремап після перестановки колонки | JS `columnId` = `c(index+1)`; заголовки можуть повторюватись. | Fingerprint впорядкованої фізичної схеми; при зміні — `needs_reconfirmation`; ніколи не зв'язувати лише за текстом. |
| Змішування корекцій і джерел | `dashboard_module_corrections` прив'язано до `module_id,row_id,field_key`, лише ім'я файла/аркуш/рядок; `row_id` не є ключем XLSX. | Не мігрувати історичні корекції; окремий row locator у межах DataVersion. |
| Пошкодження/втрата live SQLite під час rollout | `migration_startup.rs` вже має verified backup→candidate→swap і recovery; `restore.rs` перевіряє історію/цілісність. | Повторно використати цей шлях і тестувати відмови; не виконувати DDL на live напряму. |
| Відкриття чужого профілю через ID або SQL | Rust `ProfileSession` існує; SQL plugin має доступ до локальної БД для чинного SQL-режиму. | Rust-команди і FK/тригери перевіряють власника; SQL-режим залишається чинним і не є ізольованою sandbox-моделлю. Не обіцяти захист від ручного локального SQL користувача. |
| Незавершений E1-адаптер | `recommend()` позначає `catalog-v1`/`legacy` як `unsupported` за відсутності універсального адаптера. | Показати визначення й причину без створення модулів; окреме рішення D10. |

## 3. Рекомендований наступний крок після рецензії

**Перший безпечний етап:** JE затверджує D1–D10; окреме завдання E3.1 створює лише нову порожню міграцію метаданих із синтетичними тестами на копіях старої схеми та сценаріями rollback. Не підключати UI, не переносити робочі рядки, не створювати ModuleInstance. Після проходження E3.1 окремо дозволити Rust store й локальний read adapter. Це не дозвіл почати E3 зараз.

## 4. Обсяг і критерій рецензії J5

Пакет містить шість файлів у `docs/design/e3/`. J5 має звірити: FK/cascade та модель версій, підтримку 16→17 через чинний startup, відсутність третього каталогу, scope підтвердження `(source, schema, column, definition, field)`, межу preview/persistent identity, partial/stale статуси, чотири provenance шари, 20 синтетичних сценаріїв і кожне `requires_decision`. Після рецензії JE окремо вирішує міграцію й реалізацію; завершення документації не означає завершення E3.
