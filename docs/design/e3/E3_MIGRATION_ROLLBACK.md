# E3-П: міграція, резервна копія, відновлення

**Тільки план.** Жодну міграцію не створено у `src-tauri/migrations/`, не виконано на робочій SQLite і не відкрито файли користувача. Кандидат — `0017_data_source_profile_schema.sql` після перевіреного `origin/main` `3f0809b` (остання `0016`). Номер знову перевірити перед кодом.

## 1. Інвентаризація поточної бази

| Чинна частина | Власник/ключ | Вплив проєкту |
|---|---|---|
| `raw_sources`, `reports`, `parsed_report_versions`, `manual_corrections`, `review_decisions`, `revision_history`, `audit_log` (`0001`, `0002`) | Існуючий provenance-ланцюг | Ні змін, ні перенесення. Контрольні кількості/хеші до/після. |
| `local_profiles`, `local_profile_state` (`0003`) | `id` — локальний profile | Новий FK-власник E3. |
| `local_profile_tables` (`0006`–`0008`) | `(profile_id, branch)` → локальний шлях XLSX | Новий source посилається логічно на слот; стару прив'язку не змінює. |
| `dashboard_modules`, `dashboard_module_fields`, `dashboard_data_<id>` (`0010`, `0012`) | `id`, `profile_id`, `storage_table`, фізичний `row_id` | Лише read-only адаптер E3; не ALTER/DROP, не копіювати рядки. |
| `dashboard_module_corrections` (`0011`, `0016`) | `(module_id,row_id,field_key)`; raw/corrected/status | Зберегти побайтно й логічно, не перетворювати на binding. |
| `library_*`, `document_links`, інші профільні таблиці (`0013`–`0015`) | Поточні контракти | Не чіпати; включити до перевірки backup/restore. |
| `_sqlx_migrations` | історія та SHA-384 міграцій | Додати лише нову версію через чинний механізм. |

Чинний `database.rs` вбудовує SQLx-мігратор і список для `tauri-plugin-sql`; `migration_startup.rs::prepare_database()` перед Tauri робить preflight, створює перевірену передміграційну копію, мігрує **кандидат**, перевіряє його і лише тоді міняє live-файл. `restore.rs::inspect_backup()` перевіряє `integrity_check`, `foreign_key_check`, послідовність/контрольні суми міграцій та обов'язкові об'єкти; механізм обробляє sidecar і перерване перемикання. E3 має інтегруватися сюди, а не додавати другий шлях застосування DDL. Окремий `BackupStore::create_at()` уже робить локальний standalone snapshot через `VACUUM INTO`; він не замінює startup backup, але придатний для додаткової ручної копії.

## 2. Сумісність старої бази до міграції

1. Під lock одного екземпляра завершити відновлення journal/WAL через чинний `recover_live_sidecars()`. Не копіювати live `.db` окремо від WAL під час відкритих записів.
2. `inspect_backup()` має прийняти точний префікс відомих міграцій 1–16. Невідома, неуспішна або змінена за checksum міграція — **зупинити запуск/запис** і показати причину; не виконувати `0017`.
3. Зняти синтетичні контрольні свідчення у тестах: кількість/хеш записів у provenance-ланцюгу, профілях, `dashboard_modules`, динамічних таблицях, виправленнях; `PRAGMA integrity_check`, `foreign_key_check`. Для реальної БД ці перевірки локальні, не логують клітинки.
4. Якщо немає місця для перевіреної копії й кандидата — не починати міграцію. Усі зовнішні XLSX лишаються недоторканими та не входять до SQLite backup; користувачу слід окремо зберігати їхні файли.

## 3. План одноразового застосування (після дозволу JE)

1. Повторно визначити наступний номер з `origin/main`; зібрати `0017` з DDL-проєкту після рецензії. Додати його до `database::migrations()` для plugin та embedded migrator; синхронізувати `docs/DATABASE.md` і `migrations/README.md`.
2. Запустити чинний startup-процес: verified backup → тимчасова копія → SQLx міграція на копії → `inspect_backup()` із новим очікуваним списком → порівняння старого live з backup → атомарна установка кандидата. **Не** виконувати DDL безпосередньо в live-файлі; не додавати скрипт, який оминає startup.
3. DDL створює лише `e3_*`; не `DROP TABLE`, не `ALTER` старих об'єктів і не `INSERT … SELECT` старих рядків. Нові E3 таблиці після міграції порожні; профільні XLSX/старі модулі підхоплюються лише за явним вибором.
4. Після першого запуску перевірити міграційну історію, FK/цілісність, старі кількості/хеші й повторний запуск без нового запису. Увімкнення E3 UI/команд — окремий малий етап, не частина одноразового DDL.

**Межі транзакцій.** SQLx міграція кандидата має завершитися повністю до його установки; аварія під час DDL лишає live-файл і backup попередньої версії. Кожна зміна `DataSource`/schema/binding у застосунку — окрема SQLite-транзакція з CAS та квитанцією `request_id`. Читання/хеш XLSX робиться до write-lock і повторно перевіряється перед commit. Не тримати транзакцію відкритою під час діалогу користувача.

## 4. Помилка посеред міграції або перемикання

| Точка зупинки | Очікувана поведінка | Відновлення |
|---|---|---|
| До verified backup | Live не змінено. | Показати помилку, звільнити місце/усунути причину, повторити. |
| Після backup, до/під час SQLx DDL на кандидатові | Live і незмінна копія 1–16 існують; кандидат відкидається або лишається лише діагностичним. | Наступний startup повторює міграцію після перевірки backup; не «долікувати» напівсхему вручну. |
| Між `rename(live, previous)` та встановленням кандидата | Чинний код `recover_interrupted_swap()` повертає previous або завершує перевірену установку залежно від стану. | Якщо стан неоднозначний — зупинка без автоматичного видалення; ручне відновлення з verified backup. |
| Після встановлення кандидата, до фінальної перевірки | `inspect_backup()` має перевірити кандидат; при невдачі — rollback до previous. | Зберегти несправний файл для діагностики без операційних даних у логах; відновити попередній. |
| Під час E3 CAS-запису після міграції | SQLite rollback або повний commit; E3 receipt встановлюється у тій самій транзакції. | Після перезапуску перечитати версії/receipt перед повтором; не надсилати другий blind write. |

## 5. Відновлення старої бази

- Користувач обирає **перевірену** передміграційну копію. Чинний `stage_backup()`/`inspect_backup()` і offline swap перевіряють файл та не перезаписують попередній безповоротно. Перед заміною зберегти поточну 17-копію окремо для можливості повернення E3-метаданих.
- Відновлена 16-база при наступному запуску **нової** програми знову пройде 16→17 через startup; це очікувано. Якщо мета — тимчасово відкрити старою програмою, робити це лише з 16-копією й окремо від нової 17-бази. Підтвердження E3, створені **після** точки backup, у 16-копії відсутні; файл XLSX і старі корекції не змінюються.
- Не підмішувати E3-таблиці або корекції з іншої бази SQL-запитами. Перед відновленням перевірити профілі, `_sqlx_migrations`, FK, корекції й динамічні таблиці; після — повторити.

## 6. Новіша або невідома схема

Чинний `inspect_backup()` уже відхиляє невідомий/новіший ланцюг міграцій, а `DatabaseStatusStore` вимагає точного збігу списку. Політика E3: при `schema_version > supported` або іншому checksum **не відкривати базу для запису, не запускати мігратор і не робити автоматичний downgrade**. Показати локальне повідомлення з версіями та опціями встановити відповідну новішу програму або вручну обрати перевірений backup. Не запускати SQL-режим як обхід запису в такій базі.

## 7. Необхідні майбутні тести

На суто синтетичних SQLite/XLSX: міграція 1–16→17; порожня база→17; repeat startup без змін; перевірка FK й тригерів; профілі/модулі/корекції до й після; штучна SQL-помилка посеред кандидата; зупинка у кожній точці file swap; недостатнє місце; невідома версія/checksum; відновлення 16 і повторний upgrade; operation receipt після невідомого commit. Тест повинен порівняти **значення** ручних корекцій та існування `dashboard_data_*`, а не лише число таблиць.
