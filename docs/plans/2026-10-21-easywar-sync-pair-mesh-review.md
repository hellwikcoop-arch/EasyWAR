## 0. Висновок коротко

1. **Напрям сумісний із E8, комбінована синхронізація — цільова архітектура.** Майже всі інваріанти пакета J5 уже є рішеннями власника (К1–К11, Q10а–д) або збігаються з планами A4–A8. Паралельної системи створювати не треба й не можна: Pair — це деталізація «Вступу» з `COLLECTIVES_PLAN.md` §6; Sync — розширення §5.3/§5.6; Mesh у LAN — це вже запланований етап **C6 «LAN-посередники»**.
2. **Три речі в пакеті виходять за межі чинних правил.** Вони лишаються в цільовій архітектурі, але **не активуються**, доки JE не прийме відповідне рішення:
   - **`AUTO_AFTER_LOCAL_APPROVAL` (автовідправка)** — суперечить `AGENTS.md` («Any other automatic transfer needs a new owner decision and an edit here») і рішенню Q10г/§5.3 («перед відправкою показує, що саме піде»).
   - **WAN P2P, WAN-relay і store-and-forward на чужому EasyWAR** — нового транспорту немає в таблиці дозволених транспортів (§4: лише Base44 з E2E і LAN) і в етапах C0–C7.
   - **Rendezvous для короткого коду через інтернет** — це новий онлайн-сервіс (або нова сутність Base44), тобто нова зовнішня інтеграція.
3. **Інтеграція без нової лінійки етапів.** H0–H7 J5 розкладаються на наявні C0–C7, A4–A8 і P1; додається лише один новий етап **C8 «WAN-mesh (лабораторія, поза v1)»** і підетапи. Перелік — розділ 4.
4. **Знайдено дві розбіжності в чинних документах** (не в J5): `COLLECTIVES_PLAN.md` §7 називає міграції `0013_*`, хоча 0013–0016 уже зайняті (наступна вільна на `3f0809b` — **0017**); план A4 об'єднує C1 і C3 в одну задачу, а `COLLECTIVES_PLAN.md` §8 ставить C3 після C2. Обидві — bounded amendment у H0.
5. **Перший дозволений крок — лише H0 (документи).** Будь-який код E8 чекає окремого рішення JE «старт C1» (розділ 5, JE-01).

### ADR-C01. Вступ за коротким кодом (Pair)

**Контекст.** Власник хоче додавати учасників кодом, який диктують по телефону (напрям, Q01). Чинні рішення: взаємна згода (Q10в), підробних ID не може бути, новий учасник отримує всю історію й ключі всіх епох (К3), додає той, хто має ці ключі. Короткий код має мало ентропії (6 цифр ≈ 20 біт), тому не може бути ні ключем, ні доказом особи.

**Рішення (пропоноване).**
1. Код — **локатор заявки й пароль для PAKE**, не секрет доступу. Членство виникає лише з підписаного акту вступу після двох підтверджень і порівняння SAS.
2. Протокол: стандартний збалансований PAKE (кандидати для огляду в C2a: CPace або SPAKE2 — реалізації з відкритим аудитом). Із транскрипту PAKE + публічних ключів обох сторін виводиться **SAS** (наприклад, 4 слова з українського списку або 6 цифр — формат вирішує JE-07). Сторони звіряють SAS голосом.
3. Нова сторона генерує **власну** ідентичність (ADR-C05); ключі колективу ніколи не проходять через локатор/rendezvous.
4. Групове запрошення: `max_joins`, `expires_at`; **кожен** вступ — окрема заявка, окремий SAS, окреме підтвердження запрошувача. Автоприйняття немає.
5. Підтверджує конкретного заявника той, хто запросив, або інший учасник із **усіма** епохами ключів (К3). Без них — `PENDING_HISTORY`, а не `COMPLETE`.
6. У v1 підтвердження лише **онлайн** (обидва клієнти доступні одночасно). Якщо запрошувач офлайн — `WAITING_FOR_APPROVAL`, ключі не видаються (R5).
7. **Доставка заявки — змінний канал за тим самим протоколом.** Майбутня можливість: вступ за кодом через інтернет через погоджений rendezvous (JE-09); rendezvous бачить лише непрозорий ID запрошення й шифротекст PAKE, ніколи код, ключі колективу чи членство. Доки JE-09 не прийнято, активний лише LAN (⛔ C03). Пошук у LAN: ручне введення адреси або mDNS (нова залежність, C2a/JE-17). Код у mDNS-оголошенні **не транслюється**.
8. Для профілю без пароля колектив і Pair вимкнені (§6, «Сховище секретів»).

**Машина станів** (як у J5, з уточненнями):
`DRAFT → ACTIVE → JOIN_REQUESTED → SAS_VERIFIED → APPROVED_BOTH → MEMBERSHIP_RECORDED → KEYS_DISTRIBUTED → HISTORY_VERIFIED → COMPLETE`; гілки `EXPIRED`, `REVOKED`, `REJECTED`, `RATE_LIMITED`, `WAITING_FOR_APPROVAL`, `PENDING_HISTORY`, `ERROR_RETRYABLE`. Уточнення J3: `HISTORY_VERIFIED` для класу D означає «отримано по LAN»; якщо LAN-доступу до D-історії немає, учасник лишається в `PENDING_HISTORY` **лише для D-таблиць**, а A–C працюють — це треба показувати окремо по таблицях, а не одним статусом (JE-08а).

**Інваріанти.** Код ≠ ключ ≠ доказ особи. Жодних ключів до `MEMBERSHIP_RECORDED`. Невдалий SAS → `REJECTED` + запис в `audit_log`, без повторного прив'язування того самого запиту. Ліміт спроб на код і на запрошення; повтор заявки з тим самим `request_id` ідемпотентний.

**Альтернативи.** (а) QR-код замість голосу — сильніший канал, але власник хоче телефон; можна додати пізніше як другий спосіб. (б) Довгий код (10+ символів) без PAKE — гірше для диктування. (в) Код як симетричний ключ — **відкинуто** (офлайн-підбір).

**Наслідки.** Потрібна нова криптозалежність (PAKE) — К9. Потрібен LAN-канал до C6. Rate limit у v1 лише локальний (на запрошувачі); глобальний з'являється тільки з rendezvous.

**Відкрите для JE:** JE-02 (записати напрям), JE-07 (формат коду/SAS, TTL, ліміти), JE-08 (офлайн-заявки), JE-09 (rendezvous), JE-17 (mDNS).

**Перевірки (синтетика):** P01–P05 J5; плюс P06 «SAS не збігся», P07 «той самий `request_id` двічі», P08 «запрошувач без старих епох → `PENDING_HISTORY`», P09 «профіль без пароля — Pair недоступний».

### ADR-C02. Політики обміну на спільну таблицю (Sync Policies)

**Контекст.** Чинна модель: «Доповісти» з показом «було → стане» і підтвердженням (Q10г), автоматичне отримання (К2), застосування в усіх. J5 пропонує дві незалежні політики й автоматичну відправку.

**Рішення (пропоноване).** Цільова архітектура — **комбінована синхронізація** J5: дві незалежні політики на таблицю. Активація кожного значення залежить від рішення JE; до нього діє лише чинна поведінка `COLLECTIVES_PLAN.md` (§5.3 «Доповісти» з показом, §5.6 автоматичне отримання).
1. `OutboundPolicy ∈ {AUTO_AFTER_LOCAL_APPROVAL, REVIEW_EACH_REPORT, DISABLED}`. Чинній поведінці відповідає `REVIEW_EACH_REPORT`. `AUTO_AFTER_LOCAL_APPROVAL` не активне: Rust відхиляє його (`OwnerDecisionRequired`) до JE-03 і правки `AGENTS.md` (⛔ C01). Чи доступне `DISABLED` як вибір таблиці — частина JE-04/JE-06.
2. `InboundPolicy ∈ {AUTO_APPLY_VERIFIED, REVIEW_BEFORE_APPLY, DISABLED}`. Чинному «оновлює спільну таблицю в усіх» відповідає `AUTO_APPLY_VERIFIED`. `REVIEW_BEFORE_APPLY` і `DISABLED` не активні до JE-04.
3. Навіть за `AUTO_APPLY_VERIFIED` автоматично **не** застосовуються: невідома `schema_version`, `SCHEMA_CHANGE`, `MEMBERSHIP_CHANGE` без перевіреного ланцюжка повноважень, пакет із невалідним підписом/епохою, операції, що створюють конфлікт. Вони йдуть у карантин/конфлікт із показом людині. `DELETE` — за JE-05а.
4. Політику таблиці змінює власник таблиці або адміністратор (як структуру, К6); зміна — підписана операція в журналі, видима всім. Політика **не** дає права запису.
5. Порядок перевірки в Rust (⛔ C05): `networkPolicy(profile, purpose)` → `routeFor(class, transport)` → `syncPolicy(table, direction)` → членство/право запису автора → підпис/епоха/AEAD → `base_version`. Перевірка повторюється **безпосередньо перед відправкою**, а не лише при постановці в чергу.
6. Статуси (українською в UI): `Локально збережено` → `Очікує «Доповісти»` → `У черзі` → `Передано вузлу` / `Збережено у сховищі` → `Отримано й перевірено` → `Очікує приймання` / `Конфлікт` / `Карантин` / `Застосовано на цьому пристрої`; окремо `Остання успішна звірка`.

**Інваріанти.** Повний рядок у UPSERT; без LWW; `op_id`+digest; що показано в «Доповісти» — те й піде (AC05); UI не перевизначає Rust.

**Альтернативи.** (а) Прийняти AUTO-відправку зараз — неможливо без правки `AGENTS.md`. (б) Глобальна політика на колектив, а не на таблицю — простіше, але не дає власнику таблиці контролю (К6).

**Наслідки.** Таблиця `sync_policies` у C3 з `policy_version`; тести на кожну комбінацію (S01–S02) пишуться так, щоб заборонені комбінації давали відмову.

**Відкрите для JE:** JE-03, JE-04, JE-05а, JE-06 (DISABLED і фоновий pull).

**Перевірки:** S01 (як негативний тест: AUTO → відмова), S02–S08 J5; S09 «політику змінив учасник без права» → відмова; S10 «політику змінено між постановкою в чергу і відправкою» → повторна перевірка зупиняє відправку.

### ADR-C03. Посередник (Mesh Relay) — розширення `lan-relay-handover.md`

**Контекст.** C6 «LAN-посередники» і A8 уже передбачають посередника в LAN, явного host і контрольований handover. J5 додає явний opt-in власника ПК і WAN-relay.

**Рішення (пропоноване).**
1. **v1: лише LAN.** Роль RELAY вмикає власник комп'ютера окремим перемикачем «Пересилати зашифровані пакети колективу» з показом трафіку й кнопкою вимкнення. За замовчуванням вимкнено.
2. Посередник пересилає лише **автентифіковані** пакети учасників **того самого колективу**, членом якого він є (R3 default). Ключів чужих колективів, SQLite, SQL-команд не отримує. E2E-перевірка на одержувачі обов'язкова попри транспортне шифрування.
3. Авторитет membership/key-epoch у LAN — **явно призначений host** з підписаним handover; повернення старого host не створює другого джерела (M08). Автовиборів немає.
4. Прийом мережевих даних — у мінімальному Rust-модулі з лімітами розміру, кількості з'єднань, часу й пам'яті; парсер не має доступу до команд Tauri. Окремий процес (sidecar) — варіант для JE-17, не обов'язковий у v1.
5. Відкриття портів firewall/UPnP — **ні**. Windows і macOS при першому прослуховуванні показують системний запит на вхідні з'єднання — це треба описати в `USER_GUIDE.md` і перевірити на обох ОС (Linux-сесія цього не перевіряє).
6. **WAN-relay** (libp2p Circuit Relay v2 чи інше) — лише етап C8, лабораторія, після JE-05 і crate/security review. За J5, Circuit Relay v2 — онлайн-пересилання без зберігання (не перевірено мною).

**Альтернативи.** Base44 як єдиний посередник для A–C (уже план C4); прямий LAN без посередника (C6a) — завжди перший варіант.

**Наслідки.** Новий listener → залежить від P1 і P2-1 (⛔ C04).

**Відкрите для JE:** JE-05, JE-10, JE-11, JE-17.

**Перевірки:** M03, M05, M06, M08 (LAN); M01 — лише в C8.

### ADR-C04. Тимчасове зберігання (Store-and-Forward)

**Контекст.** Без одночасно онлайн учасників LAN-обмін зупиняється; Base44 вирішує це для A–C (C4), для D у v1 — ні.

**Рішення (пропоноване).**
1. Роль STORE_FORWARD — **окремий** opt-in від RELAY, з квотою диска, TTL і показом обсягу. За замовчуванням вимкнено. Стартові лабораторні параметри J5 (≤ 100 МБ, TTL ≤ 24 год) — лише для синтетичного прототипу, остаточні — після вимірювань (JE-10).
2. Контракт `put / fetch / ack` як у J5 §6.3; ключ унікальності `(recipient_scope, envelope_id, digest)`; при переповненні — чесне `REJECTED_CAPACITY`, відправник не видаляє свою копію.
3. Зберігається **лише ciphertext**; вузол — член того самого колективу (R3). Квитанція `STORED` підписана вузлом; вона не означає `APPLIED`.
4. Для класу D — лише вузол у LAN, член колективу (JE-19).
5. Base44-mailbox (C4) — той самий контракт `put/fetch/ack`, щоб транспорт замінювався без зміни формату операцій (вимога ризику «Base44 у beta» з §12).
6. При вимкненні ролі: нові `put` відхиляються; наявні пакети доставляються до TTL або очищуються за підтвердженням власника ПК; користувачу сказано, що вже передане іншим не відкликається.

**Альтернативи.** Лише Base44 для асинхронності (D тоді працює тільки онлайн у LAN) — найпростіше для v1; JE може обрати це, і тоді C6c відкладається.

**Відкрите для JE:** JE-10, JE-19, JE-20 (чи потрібен C6c у v1 взагалі).

**Перевірки:** M02, M06, S06; Q-тести на квоту, TTL, перезапуск вузла, втрату квитанції.

### ADR-C05. Криптопрофіль і ідентичність (`collective-crypto.md`)

**Контекст.** К9: перелік нових крейтів подається перед C2 і затверджується окремо. Наявні: `chacha20poly1305`, `hkdf`, `hmac`, `sha2`, `argon2`, `zeroize` (використовуються бібліотекою «Офісу»). Бракує підписів, обміну ключами, PAKE, канонічного кодування.

**Рішення (пропоноване, усе — кандидати для огляду в C2a).**

| Потреба | Кандидат | Наявне |
|---|---|---|
| Підпис пристрою/учасника | Ed25519 (`ed25519-dalek`) | — |
| Обгортка ключа епохи для учасника | HPKE (RFC 9180, крейт `hpke`) або X25519 (`x25519-dalek`) + HKDF + ChaCha20-Poly1305 | HKDF, ChaCha20-Poly1305 |
| Шифрування операцій | XChaCha20-Poly1305 (той самий `chacha20poly1305`, випадковий 192-бітний nonce) | є |
| PAKE для Pair | CPace або SPAKE2 | — |
| Канонічне кодування для підпису | детермінований формат (CBOR deterministic або власна фіксована бінарна схема з версією) — вибір у C2a | — |
| Ключ, що захищає секрети профілю | Argon2id від пароля профілю (як §6) | `argon2` |
| Затирання секретів | `zeroize` | є |

Ідентичність: **ключ учасника** (на профіль у колективі) + **ключ пристрою**, підписаний ключем учасника; ID учасника — відбиток публічного ключа (§6). Не виводити з MAC/IMEI/серійних номерів і не використовувати як ID лічильника К11. Ключ колективу «Офісу» і ключі колективу розділені контекстом HKDF.

Обов'язково в ADR: версія протоколу; AAD = усі відкриті поля заголовка (без `class_hint`, ⛔ C06); політика nonce; anti-replay (журнал `op_id`+digest); test vectors, однакові на Windows і macOS (G06); помилки без витоку деталей.

**Наслідки.** Зміна `Cargo.toml`/`Cargo.lock` — одним виконавцем, після JE-15, з `cargo audit` у CI.

**Відкрите для JE:** JE-15 (перелік крейтів), JE-18 (Keychain/Credential Manager чи файл з Argon2id).

**Перевірки:** вектори; зміна байта ciphertext/заголовка/підпису → відмова; невідома епоха; пошкоджена обгортка; відкликаний автор із backdated `client_time`; G06, G11.

## 4. Поетапний план для Codex

**Правила для всіх задач.** Одна задача = одна гілка `codex/<ew-id>-<тема>` або `claude/<тема>`; claim у `.codex/coordination` до запису (Codex); **один виконавець на файл/міграцію/lockfile** одночасно; лише синтетичні дані; звіт за `CLAUDE.md` «Звіт про статус»; «є код» ≠ «пройшов тест» ≠ «прийнято на ОС». Бюджет — орієнтир: одна сесія, не більше двох спроб, після другої невдачі — зупинка зі звітом. Грошових витрат жодна задача не має; створення/оплата Base44 — лише JE.

**Позначки gate:** 🟢 можна після доручення JE на H0 · 🟡 потрібне окреме рішення JE на старт етапу · 🔴 зовнішній gate (G-перевірки, платформа, організаційний дозвіл).
