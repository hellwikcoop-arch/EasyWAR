# КРОК 1 — Local-first безпека і підготовка хмарного обміну (план впровадження)

> **Для виконавців:** виконувати завдання по черзі, з перевіркою на синтетичних даних, без передачі виробничих записів на сервер.

**Мета:** встановити фактичну межу даних в EasyWAR, не порушити офлайн-функції і підготувати наявний E2EE-стек до майбутнього безкоштовного хмарного пілота.

**Архітектура:** Tauri 2 / Rust / SQLite / профільне зашифроване сховище залишаються єдиним місцем обробки робочих даних; вихідні мережеві запити проходять явні policy gates, а E2EE-конверти дозволяється відправляти лише після авторитетної перевірки в Rust. Майбутній кандидат транспорту: Cloudflare Workers + D1 + private R2, але на КРОЦІ 1 трафік реальних даних і WAN залишаються забороненими.

**Стек:** Rust, Tauri 2, SQLite, JS, Node test runner, наявні `EnvelopeV1` / `send_gate.rs`.

## Правила

- Рішення JE від 14.11.2026: локальна обробка й збереження даних; сервер може отримати тільки кінцево зашифровані пакети, але не plaintext чи ключі.
- Явне підтвердження користувача, перевірка адресата, права, членства й актуальності ключів обов'язкові перед відправкою.
- Публічні API/погода/оновлення/завантаження моделей дозволені лише зі своїм обмеженим payload; у робочій базі, координатах, нотатках і похідних даних не можна робити прихованих витоків.
- `GatePolicy::CURRENT` для WAN/Base44 не відкривати до окремого незалежного security review і рішення власника.
- Платна підписка EasyFLY Pro — окрема майбутня задача. Робота офлайн не залежить від сервера.
- Міграції застосовувати лише add-only. Не зливати незавершені PR без review на поточному SHA.

## Завдання 1. Зафіксувати фактичний baseline

**Існуючі файли:** `package.json`, `docs/ARCHITECTURE.md`, `src/workspace/easyfly/`, `src/workspace/collectives/`, `tests/`.

**Інтерфейси:** отримує поточну `main` і PR; результат — журнал SHA, відомих регресій і успішних сценаріїв.

- [ ] Зняти SHA main, список відкритих PR та результати останніх CI; звірити колізії з #183/#207/#208/#247/#256.
- [ ] Запустити локально `npm ci && npm run test:unit && npm run build` і `cargo test --manifest-path src-tauri/Cargo.toml` у підходящому середовищі. Записати точні результати; сам факт успіху CI не замінює E2E.
- [ ] Desktop smoke: профіль → EasyFLY → синтетичний пілот → запис → перезапуск → запис на місці; негативний тест недоступності сховища.
- [ ] Звірити перелік незлитих змін: не вносити їх без окремого review.

**Приймання:** відтворювана збірка, записані результати перевірок, визначено дефекти. У разі помилки дані не перезаписуються, користувач бачить повідомлення.

## Завдання 2. Впровадити реальну межу outbound-даних

**Існуючі файли:** `src-tauri/src/network_policy.rs`, `docs/adr/network-and-secret-boundaries.md`, `src/assistant/assistant-cloud.js`, `src-tauri/src/weather_online.rs`, `tests/network-boundary.test.mjs`. Інші конкретні entry points визначає інвентар Завдання 1.

**Інтерфейси:** вхід: тип конкретного мережевого виклику, контекст відкритого профілю, локальний дозвіл, технічні параметри; вихід: `Allowed` або причина відмови до мережевого I/O.

- [ ] Додати failing-тести на невідомі призначення, виклик не з `main`, неввімкнені інтеграції, приватні координати, внутрішні таблиці й фрагменти введеної історії до HTTPS.
- [ ] Розширити/інтегрувати наявну Rust-політику в потрібні фактичні точки мережевих команд; не створювати другий конфліктний контролер. Для викликів JS-каналу «Комбата» явно перевірити consent і заборонити надсилання внутрішніх записів.
- [ ] Тест мережевого mock: при відхиленні 0 переданих байтів; при дозволеній погоді/оновленні запит працює без внутрішніх даних.
- [ ] Запустити `node --test tests/network-boundary.test.mjs` та `cargo test --manifest-path src-tauri/Cargo.toml network_policy`; зафіксувати результат.

**Приймання:** позитивні сценарії інтернет-API збережені; негативні відхиляються до відправки; локальний EasyFLY працює офлайн.

## Завдання 3. Верифікувати E2EE send-gate і relay-контракти без WAN

**Існуючі файли:** `src-tauri/src/collective/{send_gate,relay,relay_auth,relay_node,epoch,envelope}.rs`, `docs/adr/collective-store-forward.md`, `docs/adr/collective-crypto.md`.

**Інтерфейси:** `put(envelope,recipient,expiry,size_limit) → stored_receipt`, `fetch(recipient,cursor,page_limit) → envelopes + next_cursor`, `ack(recipient,envelope_id,verification_receipt) → ack_status`; не підміняти `STORED` станом `APPLIED`.

- [ ] Додати синтетичний fixture зашифрованого `EnvelopeV1` та негативні тести на відсутнє членство, відкликання, прострочену епоху, підміну receipt, повторне повідомлення, TTL і квоту.
- [ ] Знайти розбіжності між чинним relay protocol та запропонованим Cloudflare API без зміни cryptosuite чи формату payload.
- [ ] `cargo test --manifest-path src-tauri/Cargo.toml collective` — очікується 0 невдалих тестів; перевірка на іншому SHA повторюється.
- [ ] Незалежний security review до відкриття WAN. Жодних production-ключів/сокетів у цьому кроці.

**Приймання:** сервер в тестовому макеті не бачить відкритих робочих даних або ключів; всі відмови fail-closed; WAN залишається disabled.

## Завдання 4. Підготувати Cloudflare free пілот, без запуску з реальними даними

**Запропоновані шляхи:** `server/cloudflare/`, `tests/cloud-mailbox.test.mjs`; не змінювати `server/kombat/`.

**Інтерфейси:** JSON/байтовий API `put/fetch/ack`, автентифікація пристрою, server-side TTL, rate limits, quota; R2 містить лише ciphertext, D1 — мінімальні метадані.

- [ ] Після ревізії тарифів, умов та регіону підготувати окремий development-обліковий запис із приватним R2 без публічного bucket і без токенів у frontend/Git.
- [ ] До першого зовнішнього виклику тести mock-server: тільки ciphertext, чужий учасник відхиляється, змішування колективів неможливе, повторний `put` ідемпотентний, overflow/expiry мають явний статус.
- [ ] Запускати лише на синтетичному контенті з локальним ручним підтвердженням; перевірити журнали й billing alerts. Відмова сервера не змінює локальну базу.

**Приймання:** синтетичний обмін `put/fetch/ack` відтворюваний, зовнішній сервер не отримує plaintext; виробничий WAN прапорець залишається вимкненим. Рішення на активацію — окремий JE gate після security review.

## Після КРОКУ 1

**КРОК 2:** завершення й стабілізація основного робочого процесу EasyWAR, зведення EasyFLY до єдиного вбудованого модуля, резервування й приймання на пристроях.

**КРОК 3:** інтеграція захищеного remote sync у UI з одержувачем, підтвердженням, квитанціями та журналом, якщо КРОК 1 пройшов security review.

**КРОК 4:** випуск і дистрибуція; EasyFLY Pro — окреме майбутнє рішення.

## Прогрес і приймання

Відсоток КРОКУ 1: 5 контрольних рубежів по 20%: (1) інвентар існуючого стану; (2) ADR архітектурного рішення; (3) покроковий план; (4) реалізація мережевої межі та синтетичного cloud-контракту; (5) тести, незалежний review і приймання. На 15.11.2026 зафіксовано ADR та план у draft PR — **2/5 = 40%**. Інвентар частковий; фактичні правки коду, локальні E2E-тести й security review не виконані. Не підвищувати прогрес без свідчення відповідного рубежу.
