# EasyWAR Codex Roadmap Implementation Plan

> **For agentic workers:** Use the host's available task-by-task implementation workflow. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Довести EasyWAR до узгодженого універсального локального застосунку з конструктором дашбордів, повторним імпортом таблиць, обліковими записами, керованим обміном колективів і адаптованими клієнтами.

**Architecture:** Поступовий міст до наявної Tauri/SQLite реалізації. Спільне джерело живить визначення модулів і незалежні екземпляри; акаунти, реєстрація копій, передача шаблонів та шифрований обмін колективів мають різні контракти й права доступу.

**Tech Stack:** Tauri 2, Rust, SQLite/sqlx, HTML/CSS/JavaScript, Vite, `node --test`; Base44 як запланована зовнішня інтеграція після перевірки придатності.

## Global Constraints

- Мова користувацького інтерфейсу — українська.
- Зберігати чотири шари: сире джерело → розібрані значення → ручні виправлення → схвалений запис. Схвалення виконує людина.
- Сирий XLSX не переписується мовчки; зміни схеми віддаються новим файлом.
- У Git, тестах і доказах — лише синтетичні дані; секрети не включати.
- Переходити поступово, зберігаючи перевірену поведінку старих вкладок.
- Міграції лише додаються. На дослідженому коміті вже зайняті номери 0001–0016; номер наступної визначати за актуальним `main`.
- Зовнішні інтеграції залишаються optional/explicit за чинним `AGENTS.md`, поки власник не затвердить точний виняток для Q12/Q13.
- Планування не скасовує зафіксоване рішення «E1 поки не починаємо» і не дозволяє автоматично весь E8. Початок реалізації — окреме завдання власника.
- Відкритий вибір не трактувати як згоду. Блокувати лише залежний етап, продовжувати дозволені незалежні роботи.

## 5. Маршрут виконання

| Контрольна точка | Склад | Доказ виходу |
|---|---|---|
| M0 — чесна база | P0, L0; потрібні межі P1 до A5 | Відомий SHA, усунені суперечності статусу, відкрита decision-таблиця |
| M1 — спільні модулі локально | L1 → L2 → L3 → L4 | Одна таблиця, два модулі, дві копії, повторний імпорт і одна підтверджена версія даних |
| M2 — повний конструктор | L5, L6, L7, L8 | Зв'язки, розширення, персоналізація, перенесення старих розкладок |
| M3 — мережеві акаунти/реєстр | A1 → A2 → A3 | Перевірений login із desktop, ізоляція, ідемпотентний облік і правдиві підписи |
| M4 — колектив локально | A4 → A5 | Права/версії/конфлікти/ключі перевірені на синтетиці |
| M5 — хмарний обмін | A6 | Два клієнти обмінюються E2EE-пакетами, повтори й втрати зв'язку не гублять зміни |
| M6 — розповсюдження модулів | A7 | Структура пройшла allowlist і рев'ю; новий загальний шаблон версійований |
| M7 — додаткові транспорти | A8 | LAN/Delta тільки в підтвердженому обсязі |
| M8 — платформи й випуск | P1 → P2, P3 → P4 | Платформні докази, збереження бази, перевірений updater; mobile write після свого приймання |

A1 можна досліджувати незалежно від завершення всіх L-завдань після дозволу на sandbox. A3 не потребує готових колективів. A7 не потребує доступу до робочих даних. Спільні lockfile, міграції, ACL та генеровані індекси змінювати послідовно.

3. Обрати **одне** завдання з пакета. Указати його ID, файли, вхід/вихід, відкриті рішення, докази приймання. Не читати весь репозиторій повторно.
4. Пропоновані інтерфейси нижче — контракт плану, а не вже наявні функції. Перед реалізацією перевірити відповідність фактичним API.
5. Для нового IPC узгодити `generate_handler!`, `build.rs COMMANDS`, capabilities; редактору Office не давати криптографію, профілі, базу чи мережеві привілеї.
6. Зупинка на незатвердженому рішенні стосується лише залежної дії. Не створювати Base44, не купувати тариф і не публікувати реліз від самого читання ROADMAP.
7. Кожне завершення: commit SHA, точні файли, команди/результат, обмеження, наступний ID. «Є код», «пройшов тест», «прийнято на ОС» — різні стани.
8. Бюджет сесії визначати в окремому наказі. Рекомендовано короткі завдання з максимум двома спробами; це не підміняє чинний контракт штабу.

## 7. Визначення готовності узгодженого рівня

- [ ] Довільна синтетична таблиця проходить підтверджене зіставлення, зберігає походження й живить кілька карток без копіювання даних на екземпляр.
- [ ] Конструктор підтримує обрані періоди, до 4 копій, незалежні стилі, порожні/помилкові/застарілі стани та погоджену перехресну фільтрацію.
- [ ] Повторний імпорт, зв'язування, видалення й експорт не стирають мовчки ручні виправлення чи джерело.
- [ ] Старі вкладки, Office, бібліотека, EasyPay, EasyFLY та КОМБАТ зберігають підтверджені можливості.
- [ ] Користувач входить на двох пристроях; акаунт, локальний профіль, пристрій та інсталяція чітко розрізняються.
- [ ] Власник бачить ідемпотентні лічильники з поясненням охоплення й активності.
- [ ] Призначений учасник надсилає доповідь; інший уповноважений клієнт застосовує її один раз, бачить автора/час; конфлікт вимагає рішення.
- [ ] Панель виконання обов'язкових доповідей працює за затвердженим O17.
- [ ] Сховище не отримує відкритий вміст колективів; заборонений клас не проходить Rust-межу транспорту.
- [ ] Q12 передає лише погоджений опис; розповсюдження шаблону проходить рев'ю, не виконує отриманий код.
- [ ] Внесення на телефоні й відображення на ПК доведені на обраних платформах; snapshot viewer не видається за синхронізацію.
- [ ] Випуск відтворюваний, має доказові підписи/статус технічного винятку, міграції, backup/restore та перевірку фактично завантажених пакетів.
