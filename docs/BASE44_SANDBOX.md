# EasyWAR × Base44: тестове підключення (пісочниця)

Статус: **інструкція для власника, нічого не створено**. Проєкту Base44 немає, коду, залежностей
і міграцій цей документ не змінює. Джерело: інструкція від 20.10.2026, надіслана власником
21.10.2026; приведена до актуальних рішень [`COLLECTIVES_PLAN.md`](COLLECTIVES_PLAN.md) і
[`MODULES_ROADMAP.md`](MODULES_ROADMAP.md). Це етап **C0** плану.

Позначки: **Рішення власника** — записано з його відповідей; **Перевірено** — звірено мною з
офіційною документацією 21.10.2026; **Не перевірено** — взято з інструкції власника, перед
виконанням звірити з документацією Base44 (назви розділів, тарифи й можливості змінюються).

## 1. Що саме підключаємо

Base44 — **необов'язковий хмарний транспорт і сховище зашифрованих операцій** між пристроями.
Локальні SQLite, профіль, таблиці та логіка лишаються в EasyWAR. Base44 не замінює локальну
мережу (LAN) і не зберігає код чи Excel-файли.

| Частина | Рішення |
|---|---|
| Дані користувача | Локально в EasyWAR / SQLite. У хмару йде лише дозволена категорія (розділ 2), зашифрована на пристрої |
| Обліковий запис | Пароль EasyWAR відкриває лише локальний профіль. Для хмарного обміну потрібна окрема автентифікація Base44 або перевірений механізм прив'язки. **Не перевірено** |
| Google | Вхід через Google можна розглянути як опцію, Google Drive не потрібен. **Не перевірено**: сторінка клієнта в документації вхід через постачальника не описує |
| Обмін | Локальна черга вихідних змін; «Доповісти» передає операції; оновлення підтягуються **автоматично при відкритті та раз на N хвилин**, кнопка «Звірити» лишається для ручного запиту (**Рішення власника**, К2) |
| Без мережі | Робота з локальними даними й чергою; передача й звірка відбудуться, коли з'явиться зв'язок |
| Шифрування | На пристрої до відправлення; Base44 одержує шифротекст і мінімальні службові поля |

Шифрування Base44 «під час передачі / на сервері» саме по собі **не є** наскрізним шифруванням
EasyWAR. Ключі, підписи, ротація після виключення учасника й відновлення доступу — окрема
робота (етапи C2–C3) до будь-яких реальних даних.

## 2. Які дані можна відправляти (за актуальним планом)

Це змінює положення оригінальної інструкції, де клас C був «лише після класифікації», а D
«поза Base44»:

- **Клас A, B** (структура, вигляд, склад колективу, обгортки ключів): дозволено, зашифровано.
- **Клас C** — усе, що вноситься після факту: втрати, час, підрозділ, витрата БП, координати,
  номер цілі, тип ПУ, результат і причина, виконавець, район і н.п.: дозволено,
  **лише з наскрізним шифруванням** (**Рішення власника**, 21.10.2026).
- **Клас D** (особовий склад, планові й попередні дані, стовпці без класу): у Base44 не
  потрапляє ні за яких умов.

Під час самої проби все одно використовуємо **лише вигадані дані**: класифікація не дозволяє
завантажувати реальні записи до закінчення перевірок G01–G11 і організаційного дозволу
командування.

## 3. Що підготувати перед реєстрацією

1. Власник вирішує, чи можна тестувати зовнішній сервіс. Беріть лише синтетичні назви,
   учасників і записи.
2. Визначити адміністратора тестового проєкту, двох тестових користувачів і одну сторонню
   тестову особу для перевірки ізоляції.
3. Перевірити поточний тариф і ліміти: серверні функції можуть вимагати платний план.
   **Не перевірено.**
4. Якщо є вимоги до місця зберігання чи обробки, перевірити їх до створення проєкту. Регіон
   зберігання не гарантує такого самого регіону обробки. **Не перевірено.**
5. Зафіксувати в технічному рішенні, що дозволено відправляти (розділ 2).

## 4. Створення ізольованого тестового застосунку (виконує власник)

1. Створити окремий проєкт, наприклад «EasyWAR Sync Sandbox». Не імпортувати весь репозиторій
   EasyWAR у конструктор Base44.
2. У налаштуваннях доступу ввімкнути вимогу входу й найзакритіший режим; перевірити фактичну
   поведінку в анонімному вікні.
3. У редакторі відкрити Dashboard → API; записати `appId` з адреси редактора, домен застосунку
   й посилання на документацію API у внутрішню конфігурацію тесту. `appId` — ідентифікатор,
   не секрет. **Не перевірено.**
4. Створити пробну сутність `TransportProbe` з полями `owner_user_id`, `collective_id`,
   `payload_marker`, `created_at`. Значення вигадані. Це перевірка доступу, а не схема
   бойової доповіді.
5. У Data → Permissions налаштувати створення, читання, зміну й видалення; заборонити
   анонімний доступ; перевірити, що учасник одного тестового колективу не бачить записів
   іншого. Наявність правила не доводить ізоляції: потрібен тест прямими запитами від обох
   користувачів.
6. Записати правила видалення тестових записів і проєкту після проби. Окремо з'ясувати
   експорт, резервування й строки зберігання.

**Не створювати персональний токен адміністратора (PAT) як спільний ключ для EasyWAR.** Він
діє від імені власника; у настільному застосунку дав би користувачам зайві повноваження.
Якщо PAT знадобиться для ізольованого адмінтесту: один застосунок, мінімальні права,
зберігати лише в захищеному середовищі адміністратора. **Не перевірено** (як у Base44
влаштовано PAT).

## 5. Пробне підключення клієнта

Окремий тестовий скрипт, **без додавання залежності до EasyWAR** до завершення проби:

```js
import { createClient } from '@base44/sdk';

const base44 = createClient({ appId: '<TEST_APP_ID>' });
await base44.auth.loginViaEmailPassword(testEmail, testPassword);
const records = await base44.entities.TransportProbe.list();
```

**Перевірено** (docs.base44.com, сторінка клієнта SDK): `createClient` приймає обов'язковий
`appId`; існують `auth.loginViaEmailPassword`, `auth.me()` і `setToken`. Та сторінка **не
описує** вхід через постачальника (Google), вихід, зберігання токена між сесіями й оновлення
токена. Це саме ті пункти, які треба довести окремо (перевірка «Вхід з настільного клієнта»).
Про роботу SDK поза браузером (Node, настільний застосунок) там немає окремої примітки.

Пароль і токен не записувати в код, GitHub чи журнали.

Транспорт для бойового EasyWAR доцільно розміщувати в Rust/Tauri, за локальною межею доступу
до SQLite та ключів. Це **не підтверджено**: треба довести, як Rust-клієнт безпечно входить
саме як поточний користувач Base44, оновлює сесію й викликає API з його правами.

**Перевірено** (docs.base44.com, сторінка серверних функцій): через SDK функція отримує
облікові дані поточного користувача автоматично, а при прямому HTTP-виклику (cURL, webhook)
«немає автентифікованого контексту користувача», і для таких випадків рекомендовано
`asServiceRole`. Тому функція, що працює з `asServiceRole`, **мусить сама перевіряти**
автентичність запиту, членство, право на конкретну операцію та ізоляцію колективів. Без цього
варіант із серверною функцією не приймати.

## 6. Майбутній контракт синхронізації (не створювати під час проби)

Пропозиція для реалізації, а не твердження, що Base44 уже гарантує потрібні обмеження.
Узгоджено з розділом 5.2 плану (оригінальна інструкція лишала відкритим, що несе операція).

| Об'єкт | Мінімальний зміст |
|---|---|
| Локальна операція | `op_id`, тип `upsert / delete / restore`, `base_version`, ключ рядка, **повний поточний рядок** (К1), автор, пристрій, час, версія схеми |
| Шифрований пакет | Вміст операції шифрується й підписується на пристрої. Відкритий заголовок: випадкові ідентифікатори для маршрутизації, `key_epoch`, версія протоколу, криптографічні параметри |
| Відповідь сервера | Окремі стани «прийнято на зберігання» та «застосовано локально»; курсор посторінкового читання; повторне відправлення `op_id` не створює дубля |
| Локальний стан | SQLite: вихідна черга, останній підтверджений курсор, отримані `op_id`, конфлікти, журнал застосування |

Не передавати відкритими полями назви таблиць, ключі рядків, значення клітинок, шляхи до
файлів і персональні дані. Навіть випадкові ідентифікатори, час запитів, кількість операцій і
зв'язки облікових записів залишають метадані в провайдера: їх теж потрібно погодити (К4).

Модуль транспорту: `src-tauri/src/collective/`; команди реєструвати в `generate_handler!`,
`src-tauri/build.rs` і `src-tauri/capabilities/default.json` (інакше падає
`tests/office-isolation.test.mjs`). Спочатку інтерфейс транспорту, потім адаптер Base44.
Службовий токен не підключати до JavaScript-фронтенду.

## 7. Перевірки придатності (відповідають G01–G08 плану)

| Перевірка | Очікуваний результат | Gate |
|---|---|---|
| Вхід з настільного клієнта | Відтворюваний вхід, оновлення сесії, вихід, безпечне зберігання токена на підтримуваних ОС | G01 |
| Ізоляція | Анонім, стороння людина й користувач іншого колективу не читають, не пишуть і не видаляють чужі пакети; перевірено прямими запитами | G02 |
| Права й відкликання | Додавання, зміна ролі й виключення працюють; після виключення планується нова епоха ключів | G02, G06 |
| Повтори й конфлікти | Однакові `op_id` не дублюють зміну; паралельні зміни не губляться мовчки; є ручне розв'язання | G03 |
| Повне отримання | Читання понад одну сторінку з курсором не пропускає операцій | G05 |
| Стійкість | Після обриву мережі черга відправляється повторно; після перезапуску курсор і стан збережені | G04 |
| Дані та ліміти | Межі розміру пакета, кількості записів, продуктивність до 100 учасників, резервування, експорт, видалення | G07, G08 |
| Криптографія | Перевірені формат пакета, підпис, ротація, відновлення, робота на цільових платформах | G06 |

Результат кожної перевірки записати як **пройдено / не пройдено / не досліджено** з коротким
доказом у `docs/evidence/collectives/` (без секретів і реальних даних). Якщо вхід або
ізоляція не доведені, до реальних доповідей не переходити.

## 8. Порядок робіт після проби

1. C0: зафіксувати рішення про категорії даних, доступи, витрати й результати проби.
2. Локальна модель (без хмари): операції, версії рядків, журнал, черга, курсор, конфлікти.
3. Криптографія й членство: ключі, підписи, запрошення, відкликання, ротація.
4. Адаптер Base44 — лише після підтвердженої авторизації, ізоляції, повторів, пагінації й
   обмежень API.
5. Інтерфейс: статус передачі, «Доповісти», «Звірити», помилки, конфлікти; фоновий обмін.

Підсумкове питання проби: чи може цей сервіс безпечно переносити зашифровані пакети між
обліковими записами EasyWAR із потрібною ізоляцією й керованими правами. До ствердної
відповіді локальна архітектура від нього не залежить.
