# Каталог стовпців, плиток і блоків (формат v1)

Статус: **крок 1 з 4** конструктора таблиць (дорожня карта — нижче). Є формат і суворий
валідатор, правило виводу стовпців із модулів і формат схеми таблиці користувача:
`src/catalog-core.js`, тести `tests/catalog-core.test.mjs`. Застосунок каталог поки не читає,
поведінка дашбордів не змінилась.

## Навіщо

Нині набір стовпців, шість карток «Основних показників» і 14 блоків дашборда ПС зашиті в код
`air.html` (те саме, з відмінностями, — у `rocket.html`). Каталог переносить їх у **дані**:
нова колонка, плитка чи вид журналу — це запис у JSON, а не правка сторінки. Код потрібен
лише для нового *типу* віджета (наприклад, діаграми Ганта).

Двигун не знає предметної області. Він працює зі **стовпцями певних типів** і
**підрахунками** над ними, тому однаково описує журнал ударів і журнал польотів бригади.

## Принципи

- **Дані, а не код.** У файлі немає виразів, формул, скриптів і посилань. Плитка — композиція
  з фіксованих частин: підрахунок × стовпець × відбір × вигляд.
- **Три шари:** `builtin` (вбудований) → `owner` (власника) → `profile` (профілю). Каталог
  шару посилається на свій шар і нижчі. Ідентифікатори не повторюються між шарами:
  власний варіант вбудованого елемента — це **новий id** з `based_on`, а не перевизначення.
  Тож оновлення застосунку не затирає чужих правок.
- **Усе користувацьке — у профілі.** Стовпці, плитки, блоки, вкладки меню й розкладка, які збирає
  користувач, лежать у шарі `profile` і належать профілю, а не модулю чи пристрою. Вбудований шар і
  шар власника для профілю лише читаються; змінити їхній елемент можна тільки скопіювавши його
  (`based_on`). Це відрізняє каталог від «Редактора модуля», де оформлення зберігається на модуль.
- **Недовірений вхід.** Каталог можна принести файлом з іншого комп’ютера. Валідатор працює
  закрито: невідомий ключ, зайвий тип, посилання в нікуди, керівний чи bidi-символ у підписі,
  перевищення ліміту — помилка, а не мовчазне виправлення. Успіх дає новий **заморожений**
  об’єкт лише з дозволених ключів.
- **Зберігається в базі.** Каталог профілю й схеми таблиць лежатимуть у SQLite профілю як перевірений
  JSON; копія схеми — на прихованому аркуші XLSX. Для цього потрібна нова міграція (крок 3); у кроці 1
  бази не чіпаємо.
- **Межі гнучкості (свідомі):** без мови формул і скриптів, без зв’язків між таблицями.
  Тип стовпця — із фіксованого набору.

## Ідентифікатори

Малі латинські літери, цифри, `.`, `_`, `-`; до 64 символів; обов’язковий префікс виду:

| Префікс | Що |
|---|---|
| `cat.` | сам каталог |
| `list.` | список значень |
| `col.` | стовпець |
| `tile.` | плитка |
| `block.` | блок дашборда |
| `kind.` | вид журналу |

Підписи, назви й значення — звичайний текст до 80 символів (ліміти кожного поля — в
`LIMITS`). Керівні, невидимі й bidi-символи відхиляються; текст нормалізується до NFC й
обрізається по краях. Порівняння підписів на дублікати (`foldLabel`) не розрізняє регістр,
пробіли й варіанти апострофа (`'` `’` `ʼ`).

## Структура файлу

```
{ format: "easywar.catalog", version: 1, id: "cat.…", title, layer,
  lists?: [list], columns?: [column], tiles?: [tile], blocks?: [block], kinds?: [kind] }
```

Невідомі ключі скрізь — помилка. `version` вищий за підтримуваний дає окрему помилку
`unsupported_version` («створено новішою версією застосунку»).

### Список значень `list`

`{ id, title, values: [{ value, label?, aliases?: [..] }], allowCustom?, based_on? }`

Від 1 до 500 значень. `value` і `aliases` не повторюються між собою (з поправкою `foldLabel`).
Якщо `allowCustom` не `true`, значення у відборах стовпців цього списку мають входити до нього.

### Стовпець `col`

`{ id, type, labels, aliases?, group?, description?, unit?, list?, min?, max?, integer?, maxLength?, based_on? }`

| Тип | Значення в клітинці | Додатково |
|---|---|---|
| `text` | текст | `maxLength` |
| `number` | число | `unit`, `min`, `max`, `integer` |
| `date` | дата `рррр-мм-дд` | |
| `time` | час `ГГ:ХХ` | |
| `duration` | тривалість у `unit` | `unit` обов’язковий: `хв` або `год`; `min`, `max`, `integer` |
| `choice` | одне значення зі списку | `list` обов’язковий |
| `multichoice` | кілька значень зі списку | `list` обов’язковий |
| `flag` | так / ні | |
| `coordinates` | координати (MGRS) | лише перевірка на наявність у відборі |

`labels` — від 1 до 8 **запропонованих варіантів заголовка**; перший — типовий. `aliases` —
додаткові назви для зіставлення (до 16). Усі `labels` та `aliases` стовпця різні. Ключ, який
не застосовується до типу (наприклад, `list` у тексту), — помилка.

### Підрахунок `measure`

`{ agg, column?, filter?, by?, grain? }`

| `agg` | Що повертає | `column` | Додатково |
|---|---|---|---|
| `count` | кількість записів | заборонений | |
| `share` | частка записів, що пройшли відбір | заборонений | `filter` обов’язковий |
| `sum`, `avg`, `max`, `min` | підсумок за числовим стовпцем | `number` або `duration` | |
| `distinct` | кількість різних значень | будь-який, крім `coordinates` | |
| `top` | найчастіше значення | `text`, `choice`, `multichoice` | лише як додатковий показник плитки |
| `peak` | найбільший підсумок за добу, тиждень чи місяць | необов’язковий числовий (без нього — кількість записів) | `by` (дата) і `grain` обов’язкові |

**Відбір** `filter` — від 1 до 8 умов `{ column, op, value? }`, з’єднаних «і». Операції: `eq`,
`ne`, `in`, `notin`, `gt`, `gte`, `lt`, `lte`, `empty`, `notempty`. `gt…lte` — лише для чисел,
тривалостей, дат і часу; `empty`/`notempty` — без `value`; для координат дозволені лише вони.
Значення перевіряється за типом стовпця: число, дата `рррр-мм-дд`, час `ГГ:ХХ`, булеве для
`flag`, а для `choice` — ще й належність до списку.

### Плитка `tile`

`{ id, label, sub?, measure, per?, visual, by?, tone, delta?, icon?, extras?, opens?, based_on? }`

- `visual` — одна з наявних у дашборді форм: `bars` (стовпчики за місяцями; до одного
  додаткового показника), `ring` (кільце частки; потрібен `share`, без `per` і `extras`),
  `pair` (лінія й пара міні-плиток; рівно два `extras`). `bars` і `pair` малюють ряд за датою,
  тому потребують `by` — стовпця дати.
- `per` — друга міра, на яку ділиться перша («наліт на борт»).
- `delta` — що вважати добрим: `up`, `down`, `warn`, `neutral`; зміну до попереднього періоду
  можна рахувати лише за `by`.
- `tone` — один із шести тонів палітри дашборда (`blue`, `amber`, `green`, `orange`, `red`,
  `grey`). Довільних кольорів немає, щоб зберегти єдиний вигляд.
- `icon` — лише ідентифікатор (`plane`, `bomb` …); невідомий малювальник підставить типову.
- `extras` — до двох показників `{ label, measure }`.
- `opens` — блок, куди веде кнопка «Докладніше».

### Блок `block`

Ключі залежать від `kind`; зайві ключі — помилка.

| `kind` | Обов’язкові | Необов’язкові |
|---|---|---|
| `tiles` | `tiles` (1–12 плиток) | |
| `dynamics` | `by` (дата), `measure`, `grain` (`day`/`week`/`month`) | |
| `breakdown` | `by` (текст, вибір, кілька, прапорець), `measure`, `shape` (`bars`/`ring`/`top`) | `limit` (1–50) |
| `heat` | `by` (час), `measure` | `across` (дата) |
| `map` | `coordinates` | |
| `table` | `columns` (1–30) | |
| `quality` | — | |

Підрахунок блоку: `count`, `sum`, `avg`, `max`, `min`, `distinct`.

Блок `tiles` — ряд плиток. Сьогоднішній блок «Основні показники» (`p-kpis`) має такий самий
вигляд, а окрема плитка як окремий блок — це блок `tiles` з однією плиткою.

### Вид журналу `kind`

`{ id, title, description?, sheet, columns: [{ column, core?, default? }], tiles?, blocks?, layout?, nav?, based_on? }`

- `sheet` — назва аркуша (до 31 символу, без `\ / ? * [ ] :`, не починається й не закінчується
  апострофом, не «History»).
- `columns` — стовпці, які пропонує вид; `core` — не можна прибрати, `default` — позначений
  одразу.
- `tiles`, `blocks` — що пропонує вид. Усе запропоноване має бути **досяжним**: стовпці, які
  читає плитка чи блок, входять до `columns` виду. Блок `tiles` містить лише плитки, які
  пропонує вид.
- `layout` — типова розкладка тієї самої форми, що й у рушії «Розташування блоків»:
  `{ rows: [{ cols: [{ w, cards: [block…] }] }] }`; до 20 рядів, до 4 колонок, `w` від 0
  до 12, кожен блок не більше разу й лише з `blocks` виду.
- `nav` — вкладки лівого меню виду (див. нижче).

#### Вкладки меню `nav`

`[{ target, label?, icon? }]`, від 1 до 12 вкладок. Перша вкладка завжди веде на дашборд:
`target: "dashboard"`, підпис «Дашборд» незмінний (його можна не вказувати; будь-який інший
підпис — помилка `nav_home_locked`), і «Дашборд» не може стояти не першим (`nav_home_first`).
Решта вкладок — переходи до блоків виду: `target` — `block.…` із `blocks` виду, кожен блок не
більше однієї вкладки, `label` обов’язковий (до 32 символів) і не повторює інші підписи меню,
зокрема «Дашборд». Підписи вільні: це налаштування користувача, воно зберігається в його профілі.
`icon` — лише ідентифікатор, як у плитки. Вкладок «База даних», «Внесення доповідей» і «Довідник»
каталог не описує — вони лишаються вбудованими розділами застосунку.

## Таблиця з обраних модулів

Конструктор працює від модулів, а не від стовпців: користувач ставить на дашборд блоки (можна
жодного, можна всі, що пропонує вид), і таблиця збирається сама. Порядок стовпців і дані
належать користувачеві, а не виду.

1. Кожен блок **вимагає** стовпці, які читає (`blockColumns`): плитка «Наліт на борт» — дату, години
   й бортовий номер. Залежності між стовпцями, потрібні різним модулям, зводяться докупи:
   до таблиці потрапляє об’єднання вимог усіх обраних блоків. Додали модуль — додались стовпці,
   яких бракувало.
2. До цього додаються ядро виду (`core: true`) і стовпці, які користувач закріпив вручну
   (`selection.columns`).
3. **Порядок.** Нова таблиця (без `selection.current`) отримує стартовий порядок виду
   (`kind.columns`) — автор виду ставить пов’язані стовпці поруч. Далі порядок задає користувач:
   у наявній таблиці його порядок зберігається, а нові стовпці стають у кінець у порядку виду.
4. **Дані не губляться.** Прибрали модуль — стовпець, який став непотрібним, але має дані
   (`selection.withData`), лишається в таблиці з позначкою `orphan`: його можна застосувати в
   складнішому чи попередньому модулі. Порожній непотрібний стовпець потрапляє в `dropped` і з
   таблиці зникає. Повернули модуль — стовпець знову «потрібен», а не «осиротілий».
5. Наприкінці конструктор записує таблицю (XLSX зі схемою) — це крок 3.

`deriveTable` повертає для кожного стовпця причину (`core`, `pinned`, перелік блоків, яким він
потрібен, `orphan`), щоб інтерфейс міг пояснити «додано, бо потрібен блоку X» чи «лишився, бо є дані».
Він лише рахує вибір і нічого не видаляє: результат застосовує викликач, і лише коли `ok`.
Вирішувати, чи показати користувачу перелік `dropped` перед зникненням порожніх стовпців, —
справа інтерфейсу.

## Схема таблиці

Таблицю користувача описує окремий документ `easywar.table` (версія 1):

```
{ format: "easywar.table", version: 1, kind: "kind.…", title?, columns: [{ column: "col.…", header? }] }
```

- Порядок `columns` — порядок користувача.
- `header` — заголовок стовпця в таблиці. Він обирається **лише із запропонованих** `labels`
  стовпця (порівняння — `foldLabel`) і записується в написанні каталогу; без `header` береться
  перший із `labels`. Заголовок поза переліком — помилка `header_not_offered`.
- Стовпці існують у каталогах і входять до виду (`unknown_column`, `column_not_in_kind`); кожен
  — один раз (`duplicate_ref`); усе ядро виду є в таблиці (`missing_core`).
- Заголовки таблиці різні (`duplicate_label`): інакше читання за заголовком було б неоднозначним.
- Схема лежить у базі профілю й копією на прихованому аркуші XLSX.

**Дашборд читає таблицю за схемою, а не за позицією стовпця**, тож порядок може бути будь-яким.
Що вже перевірено: імпорт XLSX зіставляє 15 обов’язкових заголовків без урахування пробілів і
регістру, допускає зайві стовпці й будь-який їхній порядок (покрито контрактним тестом Rust проти
legacy-ядра). Що ще ні: імпорт і дашборди поки не знають заголовків поза цими 15 полями — це робота
кроку 3.

## Обмеження

Файл не більший за 512 КіБ; не більше 200 списків, 300 стовпців, 300 плиток, 100 блоків,
50 видів; не більше 50 повідомлень про помилки (далі `truncated: true`). Усі значення —
в `LIMITS` у `catalog-core.js`.

## Програмний інтерфейс

- `parseCatalogText(text)` → `{ value, error }`: розмір, BOM, коректність JSON.
- `validateCatalog(input, { base })` → `{ ok, errors: [{ path, code, message }], truncated, catalog }`.
  `input` — об’єкт або текст; `base` — уже перевірені каталоги нижчих шарів (лише результат
  `validateCatalog().catalog`, інакше `TypeError`).
- `tileColumns(tile)`, `blockColumns(block, findTile)`, `measureColumns(measure)` — які стовпці
  потрібні, щоб конструктор міг вимикати плитку чи блок із поясненням.
- `deriveTable(catalogs, kindId, { blocks, columns, current, withData })` →
  `{ ok, columns, added, dropped, reasons, problems }`: стовпці таблиці (порядок користувача, якщо
  є `current`), що додано, що можна прибрати як порожнє, і причина кожного стовпця. `catalogs` —
  перевірений каталог або масив перевірених шарів (нижній першим), інакше `TypeError`. Проблеми
  (`unknown_kind`, `unknown_block`, `block_not_offered`, `unknown_column`, `column_not_in_kind`,
  `bad_id`) повертаються списком, а не кидаються.
- `validateTableSchema(input, catalogs)` → `{ ok, errors, truncated, schema }`: перевірка схеми
  `easywar.table` (`TABLE_FORMAT`, `TABLE_VERSION`) відносно перевірених каталогів; `input` —
  об’єкт або текст; при успіху `schema` заморожена, заголовки в написанні каталогу.
- `NAV_HOME` — перша вкладка меню (`target: "dashboard"`, підпис «Дашборд»).
- `foldLabel(text)` — ключ порівняння підписів.

## Що ще не вирішено

- **Формат v1 не заморожений.** Крок 2 (шість поточних карток як описи) може показати потребу в
  нових підрахунках, наприклад «кількість діб періоду» для «Середнього темпу».
- **Порівняння значень у відборі** (регістр, пробіли, апострофи) визначить крок обчислень;
  `foldLabel` зараз використовується лише для пошуку дублікатів.
- **Тривалість у клітинці XLSX** — число в одиницях `unit` чи формат «години:хвилини» — вирішить
  крок запису таблиці.
- **Перенесення нинішньої розкладки.** Рішення власника: каталог і схеми лежать у базі профілю.
  Лишається спосіб перенести розкладку, яка зараз у `localStorage` під ключем без ідентифікатора
  профілю, і сама міграція SQLite (крок 3).
- **Заголовки поза 15 полями.** Імпорт XLSX та 14 блоків дашборда ще не читають довільні заголовки зі
  схеми; чи парсер `air.html` зберігає стовпці поза цими полями і чи терплять усі блоки відсутність
  необов’язкових стовпців — не перевірено.
- **Скасування імпорту.** Чи можна відкликати вже підтверджену партію імпорту, коли стовпець
  зникає з таблиці, — не перевірено.
- **Припущення про меню.** У ПС ліве меню нині веде до блоків (Зведення, Карта, Вильоти…), а
  «Дашборд» — перша верхня вкладка. Формат ставить «Дашборд» першою вкладкою меню виду; якщо
  вона має бути окремим пунктом поряд із блоками, це змінює лише `nav`.

Вже вирішено власником: плитки й усі налаштування належать профілю; модулі ставляться на
дашборд поодинці (плитка — це блок `tiles` з однією плиткою, «Основні показники» — лише
групування); вкладки меню мають вільні підписи, крім першої; стовпець з даними лишається, коли
модуль прибрали; порядок стовпців визначає користувач, а дашборд читає таблицю в будь-якому
порядку; каталог і налаштування зберігаються в базі.

## Дорожня карта

1. **Формат і валідатор** (цей документ). Поведінка застосунку не змінюється.
2. Плитки як описи: шість поточних карток ПС записуються в каталозі й дають той самий вигляд
   (перевірка знімками на синтетичних даних). Підрахунок виконує чистий `tiles-core.js`.
3. Конструктор порожньої таблиці ПС за каталогом: модулі → потрібні стовпці (`deriveTable`) →
   порядок → запис XLSX зі схемою на прихованому аркуші; каталог плиток із переглядом та правкою.
4. Динамічні блоки в «Розташуванні блоків»: набір ідентифікаторів береться зі схеми.

Для РВ, ПВК, УДШВ і артилерії те саме робитиметься після ПС, на тому самому двигуні.
