# Контекст для J3: каталог модулів дашборда

## Goal

Завдання — додати до локального дашборда EasyWAR каталог аналітичних модулів,
який покриває типи візуалізацій із семи наданих користувачем референсів.

Ключовий сценарій:

1. користувач обирає тип модуля в каталозі;
2. модуль з'являється на поточному дашборді;
3. у локальній SQLite автоматично створюється окрема фізична таблиця зі
   стовпчиками, визначеними шаблоном модуля;
4. користувач додає або редагує рядки через український інтерфейс;
5. модуль будує візуалізацію з даних своєї таблиці.

Архітектурні межі: local-first, Tauri 2, Rust, SQLite з вбудованими SQLx-
міграціями та поступове розширення наявного HTML/CSS/JavaScript-інтерфейсу без
повного переписування legacy-застосунку.

## Completed

### 1. Локальна схема й міграції

- Додано міграцію `src-tauri/migrations/0010_dashboard_modules.sql` з
  метаданими модулів у `dashboard_modules` і описами полів у
  `dashboard_module_fields`.
- Міграція підключена до того самого вбудованого SQLx-migrator, який
  використовує основний застосунок. Ручного SQL-дампа схеми немає.
- Створення нової бази, перевірка поточної схеми, startup-міграція та
  відновлення резервної копії очікують уже 10 міграцій.
- Створення модуля транзакційно записує метадані й створює окрему таблицю з
  безпечно згенерованою назвою формату `dashboard_data_<24 hex symbols>`.
- Фізичні назви колонок походять лише з вбудованого Rust-каталогу. Довільний
  користувацький текст у DDL не потрапляє.
- Дані ізольовані за локальним профілем і гілкою дашборда: `air`, `rocket`,
  `pvk` або `dshv`.
- Межі: до 64 модулів на профіль/гілку, до 10 000 рядків на читання або один
  запис, до 4096 символів у текстовому полі.

переставляє старі фізичні колонки, але UI відображає логічний порядок із
метаданих.

### 4. Rust API

У `src-tauri/src/dashboard_modules.rs` реалізовано:

- отримання каталогу;

### 6. Раніше погоджені аналітичні контракти

Паралельна робота з SQLite-джерелом аналітики збережена без зміни назв:

- `result → kind`: `hit → hit`, `partial → part`, `miss → miss`,
  `unknown → unk`;
- оскільки Rust не зберігає сирий текст підрозділу, `unitRaw` отримує те саме
  канонізоване значення, що й `unit`;
- це відоме спрощення прямо зафіксовано в `docs/ANALYTICS.md`; пошуку
  «сирого» підрозділу в інших місцях немає;
- нові `.sqlite3` створюються тими самими вбудованими міграціями, що й основна
  база застосунку.

Документацію оновлено в `docs/ANALYTICS.md` і `docs/USER_GUIDE.md`, після чого
перегенеровано `src/assistant/knowledge/index.json`.

Перевірено на синтетичних даних:

```text

# успішно; лише наявні попередження про classic script і розмір chunks

cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check
# успішно

cargo check --manifest-path src-tauri/Cargo.toml --locked
# успішно

cargo test --manifest-path src-tauri/Cargo.toml dashboard_modules::tests -- --nocapture
# 5 passed, 0 failed
```

Повний Rust-набір запускали окремо:

```text
cargo test --manifest-path src-tauri/Cargo.toml --lib
# 245 passed, 1 failed, 1 ignored
```

Єдиний збій:

```text
local_model::tests::a_runner_that_never_becomes_ready_is_a_start_failure
src/local_model.rs:1227
очікувався ModelError::Start(_)
```

Цей тест не стосується каталогу модулів, але повний Rust-набір не можна
називати зеленим, доки збій не буде окремо розібрано або підтверджено як
нестабільний.

Браузерна перевірка через тимчасовий локальний harness підтвердила:

- картка створеного модуля видима;
- таблиця показує 24 поля даних плюс колонку `Дія`;
- синтетичний повний рядок з типом ПС `Су-27` додається;
- перший рядок редагується, зокрема `Наліт (загальний)` змінено на `2.5`;
- після трьох синтетичних записів прев'ю показало 3 типи ПС і 6 смуг;
- помилок у консолі браузера не було.

Під час QA знайдено й виправлено проміжне відображення `null` у DOM:
необов'язковий вузол тепер додається до `replaceChildren` через умовний spread.
Тимчасовий QA-файл після перевірки видалено.

## Risks/blockers

- Повний `cargo test --lib` має один відомий збій поза зміненим модулем.
- `replace_dashboard_module_rows` транзакційно переписує весь набір рядків, але
  тепер із перевіркою версії (`expected_updated_at`): застаріле вікно отримує
  конфлікт і нічого не перезаписує. Виклик без версії лишився безумовним
  (його не робить жоден код інтерфейсу).
- Адитивне оновлення старої фізичної таблиці виконує DDL під час першого
  читання/матеріалізації. Збереження старих рядків покрито Rust-тестом.
- Для вже наявної старої таблиці фізичний порядок колонок може не збігатися з
  новим логічним порядком; UI спирається на метадані й показує правильну
  послідовність.
- Сім фото-референсів і Markdown-постановки надходили як тимчасові вкладення з
  `/tmp/codex-remote-attachments`. Вони не є стабільною частиною репозиторію;
  для продовження слід спиратися на цей файл і код, а за потреби оригіналів
  попросити користувача прикріпити їх повторно.

## Одиниці й формати (2026-10-18, гілка `claude/dashboard-modules`)

Власник надав приклади: наліт загальний `0:32`, наліт повітря `0:22`, висота
`0.3м(300м)`, видимість `10`, паливо `255л (204кг)` (густина `0.8`; запис
«225х0.8» у повідомленні прочитано як друкарську помилку: 255 × 0,8 = 204).
Нових міграцій немає, типи колонок не змінювалися.

- Підписи: `Наліт (повітря), год:хв`, `Наліт (загальний), год:хв`,
  `Час у хмарах, год:хв`, `Час під шторкою, год:хв`, `Висота польоту, м`,
  `Видимість, км`, `Витрата палива, л`. Наявні модулі отримують їх під час першого
  читання (`synchronize_template_schema`; перевіряє
  `legacy_flight_module_is_extended_without_losing_rows`).
- Зберігання лишилось числовим: тривалість — десяткові години (`0:32` → `32/60`),
  висота — метри, паливо — літри. Кілограми не зберігаються: JS розраховує їх як
  літри × 0,8 (`FUEL_DENSITY_KG_PER_L`) і показує «255 л (204 кг)».
- Введення й показ (`dashboard-module-catalog-core.js`, поля за ключем і лише
  для `real`): тривалість — строго `год:хв` із двоцифровими хвилинами; десяткові
  години не приймаються (`1.30` легко прочитати як 1:30); висота — `300` або
  `300 м`, кілометри лише з одиницею (`0,3 км` → 300), число менше за 1 без
  одиниці відхиляється як неоднозначне; паливо — літри, не менше 0, підказка з
  кілограмами під полем.
- Правка запису не переписує незмінене поле: якщо текст у формі збігається з тим,
  з яким її відкрито, лишається збережене значення (так старі `1,42` год не
  округлюються до `1:25` мовчки). Повідомлення про помилку у формі зникає, щойно
  поле починають виправляти.
- Припущення, які варто підтвердити: висота — метри (запис `0.3м(300м)`
  прочитано як 0,3 км = 300 м); видимість — кілометри (одиниця не названа);
  `год:хв` застосовано також до часу в хмарах і під шторкою; межі хмар прийнято
  в метрах за аналогією з висотою (див. наступний розділ); запис «Вправа 2/3/6»
  — три значення для трьох полів вправ (див. «Таблиця власника»).
- Тести: +11 JS (`tests/dashboard-module-catalog.test.mjs`), +1 перевірка підписів
  у Rust-тесті. Chromium-сценарій розширено формами `год:хв`, «0,3 км», літрів і
  вузьким екраном.

## Метеоумови й екіпаж (2026-10-18, гілка `claude/dashboard-modules`)

Вимоги власника: видимість належить до метеоумов поряд із НМХ і ВМХ; хмарність
теж туди й лише 0–10; «погодні умови не змінюються кожну хвилину — раз на 5–10
записів в одну льотну зміну»; окремий пункт «екіпаж»: КЕ, ЛШ, БТ, для літака до
8 осіб, прізвища вписують. Уточнення того ж дня: на Ан-26 є радист, бортмеханік,
штурман, штурман-інструктор і помічник командира екіпажу, а інструктор можливий
у будь-кого з екіпажу, зокрема на Мі-8 — усі вони йдуть у поле «інші» (КЕ + ЛШ + БТ
+ 5 інших = 8). Нових міграцій немає: нові поля додано в кінець
шаблону Rust, наявні модулі отримують їх через `synchronize_template_schema`
(додає колонки й оновлює підписи без втрати рядків; перевіряє
`legacy_flight_module_is_extended_without_losing_rows`).

- Rust: підписи `Верхня межа хмар (ВМХ), м`, `Нижня межа хмар (НМХ), м`,
  `Хмарність, 0–10`; нові текстові поля `crew_ke`, `crew_lsh`, `crew_bt`,
  `crew_other` (роль `dimension`, агрегація `none`). Меж значень Rust не
  перевіряє свідомо: старий запис із числом поза шкалою не повинен блокувати
  збереження таблиці, тому межі лежать у формі.
- Форма (`dashboard-module-catalog-core.js`, `dashboard-module-catalog.js`):
  - `fieldSections` розкладає поля на основні, «Метеоумови» (ВМХ, НМХ, хмарність,
    видимість) і «Екіпаж»; «Політ у СМУ» лишається основним полем, бо це ознака
    польоту. Для модуля без таких полів форма не змінюється;
  - ВМХ і НМХ вводяться як висота польоту: `300`, `300 м`, `0,3 км`; НМХ вища за
    ВМХ — помилка (`checkRowRules`);
  - хмарність — ціле 0–10, видимість і паливо не менше 0 (`FIELD_LIMITS`,
    `fieldLimits`); межі перевіряє лише `parseFieldInput`, без `min`/`max` у
    полі, щоб причина відмови завжди показувалась українською у формі; старе
    значення поза межами не блокує правку іншого поля (незмінене поле
    лишається як є), а нове значення перевіряється;
  - новий запис (не правка) бере метеополя з останнього запису, де вказано хоч
    одне з них (`inheritedValues`: набір одного запису, без змішування з
    давнішими); у групі показано позначку й кнопку «Очистити»; екіпаж, час,
    наліт і СМУ не переносяться;
  - екіпаж: `crewCount` рахує прізвища за комами й крапками з комою у всіх
    чотирьох полях, максимум `MAX_CREW = 8`; лічильник «Екіпаж: N з 8 осіб»
    під полями, запис із більшою кількістю не зберігається.
- Свідомі спрощення (потребують рішення власника): погода зберігається копією в
  кожному записі, а не окремою сутністю «погода льотної зміни» — для зв'язаних
  таблиць потрібні кроки 3–4 плану конструктора, які без прямого «так» власника не
  розпочато; ліміт 8 осіб однаковий для всіх типів ПС (тип ПС — вільний текст);
  екіпаж — перший варіант (КЕ, ЛШ, БТ і одне поле «інші» через кому).
- Тести: +12 JS (`tests/dashboard-module-catalog.test.mjs`, разом 41 у файлі), Rust-
  тест розширено ключами й підписами нових полів; Chromium-сценарій (синтетичні
  дані, імітація бекенда) доповнено групами, підстановкою погоди, «Очистити»,
  межами хмарності, лічильником екіпажу, старим значенням 75 і вузьким екраном.
- Не перевірено: macOS і Windows; інтерфейс у справжньому вікні Tauri (зокрема
  поведінка форм у WKWebView).
