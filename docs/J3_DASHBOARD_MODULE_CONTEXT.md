# Контекст для J3: каталог модулів дашборда

## Goal

Завдання — додати до локального дашборда EasyWAR каталог аналітичних модулів,
який покриває типи візуалізацій із семи наданих користувачем референсів.

Ключовий сценарій:

1. користувач обирає тип модуля в каталозі;
2. модуль з'являється на поточному дашборді;
3. у локальній SQLite автоматично створюється окрема фізична таблиця зі
   стовпчиками, визначеними шаблоном модуля;
4. користувач додає або редагує рядки через український інтерфейс;
5. модуль будує візуалізацію з даних своєї таблиці.

Архітектурні межі: local-first, Tauri 2, Rust, SQLite з вбудованими SQLx-
міграціями та поступове розширення наявного HTML/CSS/JavaScript-інтерфейсу без
повного переписування legacy-застосунку.

- Додано міграцію `src-tauri/migrations/0010_dashboard_modules.sql` з
  метаданими модулів у `dashboard_modules` і описами полів у
  `dashboard_module_fields`.
- Міграція підключена до того самого вбудованого SQLx-migrator, який
  використовує основний застосунок. Ручного SQL-дампа схеми немає.
- Створення нової бази, перевірка поточної схеми, startup-міграція та
  відновлення резервної копії очікують уже 10 міграцій.
- Створення модуля транзакційно записує метадані й створює окрему таблицю з
  безпечно згенерованою назвою формату `dashboard_data_<24 hex symbols>`.
- Фізичні назви колонок походять лише з вбудованого Rust-каталогу. Довільний
  користувацький текст у DDL не потрапляє.
- Дані ізольовані за локальним профілем і гілкою дашборда: `air`, `rocket`,
  `pvk` або `dshv`.
- Межі: до 64 модулів на профіль/гілку, до 10 000 рядків на читання або один
  запис, до 4096 символів у текстовому полі.

переставляє старі фізичні колонки, але UI відображає логічний порядок із
метаданих.

### 4. Rust API

У `src-tauri/src/dashboard_modules.rs` реалізовано:

- отримання каталогу;
- перелік модулів поточної гілки;
- транзакційне створення модуля і його фізичної таблиці;
- читання даних із валідацією схеми;
- повну транзакційну заміну рядків;

- автоматичне адитивне оновлення старого шаблону нальоту.

Команди зареєстровані в Tauri через `src-tauri/src/lib.rs`.

### 6. Раніше погоджені аналітичні контракти

Паралельна робота з SQLite-джерелом аналітики збережена без зміни назв:

- `result → kind`: `hit → hit`, `partial → part`, `miss → miss`,
  `unknown → unk`;
- оскільки Rust не зберігає сирий текст підрозділу, `unitRaw` отримує те саме
  канонізоване значення, що й `unit`;
- це відоме спрощення прямо зафіксовано в `docs/ANALYTICS.md`; пошуку
  «сирого» підрозділу в інших місцях немає;
- нові `.sqlite3` створюються тими самими вбудованими міграціями, що й основна
  база застосунку.

Документацію оновлено в `docs/ANALYTICS.md` і `docs/USER_GUIDE.md`, після чого
перегенеровано `src/assistant/knowledge/index.json`.

## Validation

Перевірено на синтетичних даних:

```text
npm run test:unit
# 751 passed, 0 failed

npm run build
# успішно; лише наявні попередження про classic script і розмір chunks

cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check
# успішно

cargo check --manifest-path src-tauri/Cargo.toml --locked
# успішно

cargo test --manifest-path src-tauri/Cargo.toml dashboard_modules::tests -- --nocapture
# 5 passed, 0 failed
```

Повний Rust-набір запускали окремо:

```text
cargo test --manifest-path src-tauri/Cargo.toml --lib
# 245 passed, 1 failed, 1 ignored
```

Єдиний збій:

```text
local_model::tests::a_runner_that_never_becomes_ready_is_a_start_failure
src/local_model.rs:1227
очікувався ModelError::Start(_)
```

Цей тест не стосується каталогу модулів, але повний Rust-набір не можна
називати зеленим, доки збій не буде окремо розібрано або підтверджено як
нестабільний.

Браузерна перевірка через тимчасовий локальний harness підтвердила:

- картка створеного модуля видима;
- таблиця показує 24 поля даних плюс колонку `Дія`;
- синтетичний повний рядок з типом ПС `Су-27` додається;
- перший рядок редагується, зокрема `Наліт (загальний)` змінено на `2.5`;
- після трьох синтетичних записів прев'ю показало 3 типи ПС і 6 смуг;
- помилок у консолі браузера не було.

Під час QA знайдено й виправлено проміжне відображення `null` у DOM:
необов'язковий вузол тепер додається до `replaceChildren` через умовний spread.
Тимчасовий QA-файл після перевірки видалено.

## Risks/blockers

- Повний `cargo test --lib` має один відомий збій поза зміненим модулем.
- `replace_dashboard_module_rows` транзакційно переписує весь набір рядків, але
  тепер із перевіркою версії (`expected_updated_at`): застаріле вікно отримує
  конфлікт і нічого не перезаписує. Версія обов'язкова: виклик без неї чи з
  порожньою версією відхиляється (`VersionRequired`) і нічого не змінює.
- Адитивне оновлення старої фізичної таблиці виконує DDL під час першого
  читання/матеріалізації. Збереження старих рядків покрито Rust-тестом.
- Для вже наявної старої таблиці фізичний порядок колонок може не збігатися з
  новим логічним порядком; UI спирається на метадані й показує правильну
  послідовність.
- Сім фото-референсів і Markdown-постановки надходили як тимчасові вкладення з
  `/tmp/codex-remote-attachments`. Вони не є стабільною частиною репозиторію;
  для продовження слід спиратися на цей файл і код, а за потреби оригіналів
  попросити користувача прикріпити їх повторно.

  колонок закріплена). Escape спершу скасовує рядок, що редагується, потім повертає
  на дашборд; фокус повертається на кнопку модуля. Після додавання таблиця гортається
  до нового рядка, після правки чи видалення лишається на місці. Сповіщення
  додається всередину відкритого діалогу, бо `<body>` закритий шаром поверх.
- **Назва.** У каталозі Rust шаблон `flight-hours` тепер називається «Журнал
  хронометражу польотів». Модуль, створений зі старою типовою назвою «Загальний наліт
  за типом ПС», показується з новою (`moduleTitle` у `normalizeModules`); збережена
  назва в базі не переписується, а назва, яку змінив користувач, не чіпається.
- **Тести.** JS: 52 у `tests/dashboard-module-catalog.test.mjs` (нові — назва, сторінка,
  Escape, переходи, ширини, `FieldValueError`); Rust: перевірка назви в
  `create_builds_a_physical_table_with_template_columns`. Chromium-сценарії на
  синтетичному моку (поза репозиторієм): запис в один рядок — 18 перевірок,
  сторінка на 60 рядках — 11 (на весь екран, закріплена шапка, запис у кінці, сповіщення
  поверх, збереження позиції, Escape, вузький екран, світла тема).
- Припущення, які варто підтвердити: «в одну лінію» означає всі 35 полів у одному
  рядку таблиці (а не лише основні поля); «сторінка» — повноекранний вигляд із
  поверненням на дашборд, а не окремий маршрут чи вікно Tauri (окреме вікно потребувало
  б змін capabilities, які без рішення власника не робляться).
- Не перевірено: macOS і Windows; інтерфейс у справжньому вікні Tauri (WKWebView,
  WebView2): неявне надсилання форми через атрибут `form`, `scroll-padding` під час
  фокуса, `color-mix`, поведінка `<dialog>` у вкладеному iframe лаунчера.

## Дані з таблиці під час створення модуля (2026-10-18, гілка `claude/dashboard-modules`)

Вимога власника: «А треба щоб воно при створені брало дані з таблиці яку ми додали
якщо вони там є, якщо немає то додавався стовпчик в який ці дані починають
вноситись». Тлумачення: під час створення модуля EasyWAR читає таблицю XLSX, яку
прив'язано до профілю (або файл, який користувач обере), знаходить аркуш зі
схожими заголовками й підтягує з нього записи; колонки модуля, яких у таблиці
немає, лишаються в модулі порожніми, і дані в них вносять у самому модулі. У
сам XLSX нічого не пишеться. Запис нових стовпців у файл власника, приховані
аркуші зі схемою, динамічні блоки й зв'язані таблиці (кроки 3–4 плану
конструктора) без прямого «так» власника не робилися.

- **Rust.**
  - `src-tauri/src/module_source.rs` — читач лише для читання (`calamine`, та сама
    закріплена версія, що й в імпорті): видимі аркуші, лише непорожні рядки з
    номером рядка Excel, не більше 10 000 + 50 рядків заголовків, огляд аркуша
    повертає 25 перших рядків. Клітинка — `null`, рядок, число або логічне;
    тривалість Excel віддається рядком `Г:ХХ`, час доби — `ГГ:ХХ`, дата й дата з
    часом — `РРРР-ММ-ДД[ ГГ:ХХ]`. Читач не пише файлів і нічого не змінює.
  - Команди: `inspect_linked_module_source(branch)` (таблиця профілю для цього
    дашборда; `null`, якщо не прив'язано), `pick_module_source()` (вікно вибору
    `.xlsx`; шлях лишається лише в пам'яті Rust, `ModuleSourceSelection`, від
    інтерфейсу шляхи не приймаються), `read_module_source_sheet(origin, branch,
    sheet)` (`origin` — `linked` або `picked`). Розмір файла й розширення
    перевіряє наявний `read_selected_xlsx` (64 МБ).
  - `create_dashboard_module(..., rows?)` створює модуль і записи однією
    транзакцією (`create_with_rows`): записи перевіряються тим самим
    `validate_value` до створення, некоректний запис або понад 10 000 записів не
    лишають нічого (ні метаданих, ні таблиці). Без `rows` поведінка не змінилася.
  - Міграцій, нових залежностей, змін capabilities Tauri чи CSP немає.
- **JS.** `src/dashboard-module-source-core.js` (чиста логіка, без DOM і Tauri) і
  блок «Дані з вашої таблиці» у вікні створення (`sourceBlock` у
  `dashboard-module-catalog.js`). Правила форми, що зв'язують поля запису (НМХ не
  вища за ВМХ, екіпаж до 8 осіб), винесено в `rowRuleProblem` без винятків: форма
  їх, як і раніше, кидає, а підтягування лише попереджає й записи лишає.
- **Інтерфейс.** Блок стоїть у лівій колонці форми під назвою модуля (праворуч —
  довгий список колонок нової таблиці). Стани: «Шукаю таблицю профілю…», «таблицю
  не підключено» з кнопкою «Обрати файл XLSX…», помилка читання, «немає аркуша зі
  схожими стовпцями», готово. У стані «готово» — вибір аркуша (якщо їх кілька),
  підсумок («Буде підтягнуто N записів. Знайдено стовпців: 34 з 35.»), примітки
  (нові стовпці модуля, не використані стовпці таблиці, пропущені рядки,
  клітинки, яких не вдалося розібрати, зауваження правил форми), галочка
  «Підтягнути N записів у новий модуль», друга галочка «Протягнути метеоумови на N
  записів тієї ж льотної зміни, де їх не вказано» (лише коли є на що протягувати;
  за умовчанням увімкнена; неактивна, поки знято головну) і два розділи, що
  розгортаються: відповідність стовпців і перший запис у збереженому вигляді. Кнопка створення
  неактивна, поки таблицю читають; після закриття вікна пізні відповіді
  відкидаються.
- **Зіставлення заголовків.** Заголовки порівнюються без регістру, пунктуації,
  розривів рядка й латинських двійників літер усередині кириличних слів (`№` →
  «номер»). Кандидати: повний заголовок, без одиниці виміру в кінці, без дужок,
  обидва варіанти; назви беруться з підпису поля шаблону, словника назв журналу
  польотів (колонки таблиці власника, з розділу «Таблиця власника» вище) і
  загального словника. Рядок заголовків шукається серед перших 25 рядків аркуша
  (потрібно щонайменше два збіги), тож назва аркуша чи порожні рядки зверху не
  заважають. Повторені колонки «Вправа» йдуть за порядком (КБП, №1, №2), кілька
  колонок «Інший екіпаж» зливаються в одне поле через кому, метеоумови однією
  клітинкою розкладаються на хмарність, НМХ, ВМХ і видимість (рівно чотири числа в
  цьому порядку; окремі колонки мають перевагу). Аркуш «схожий» (`confident`), коли
  знайдено всі обов'язкові поля й щонайменше `min(5, ⌈0,6 · кількість полів⌉)`
  полів; лише тоді галочка підтягування вмикається сама.
- **Значення.** Нічого не вгадується: тривалості читаються лише як `Г:ХХ` (число
  без двокрапки неоднозначне); висота — `300`, `300м`, `0,3 км`, `0.3м(300м)`, а
  `0,3` без одиниці відхиляється; паливо — літри (`310`, `310 л`, `310л (248кг)`,
  `310/248` за відношенням кг/л від 0,7 до 0,9), запис лише в кілограмах
  відхиляється; видимість — кілометри (метри перераховуються); зліт і посадка →
  `ГГ:ХХ`; «Так»/СМУ → true, «Ні»/ПМУ → false, прочерк → порожньо; дати за
  стандартом. Рядки «Разом», «Всього», «Усього», «Підсумок», «Загалом» пропускаються;
  рядок без обов'язкового значення (або з нерозібраним) пропускається з причиною,
  яка підсумовується («Пропущено 2 рядки: …»); нерозібрана клітинка
  необов'язкового поля лишає поле порожнім і потрапляє в попередження з колонкою,
  першим рядком Excel і причиною. Понад 10 000 записів — перші 10 000 з
  попередженням.
- **Метеоумови протягуються (2026-10-19).** Питання власника було: у таблиці погода
  стоїть у кожному рядку чи раз на льотну зміну, і чи протягувати її на наступні
  рядки зміни. Відповідь: «може змінитись на якомусь із польотів». Тому погода
  діє, доки таблиця не дасть нове значення, і лише в межах однієї льотної зміни:
  - запис без метеоумов (усі чотири поля порожні) бере набір метеоумов
    найближчого попереднього запису, якщо в обох однаковий номер льотної зміни
    (`flight_shift_number`); власне значення таблиці завжди головніше, а погода
    переходить цілим набором одного запису, без домішок з давніших (запис лише з
    видимістю передає далі лише видимість);
  - не протягується: через зміну льотної зміни; коли номера зміни немає в записі
    чи в таблиці (межі зміни невідомі, а вгадувати їх не можна); після клітинки
    метеоумов, яку не вдалося розібрати (погода з того місця невідома, попередня
    не підставляється); погода, що порушує правило НМХ/ВМХ (помилку не
    розмножуємо). Блок називає, скільком записам і з якого рядка метеоумови
    протягнуто, і скільком не вдалося (з першим таким рядком);
  - рядок, пропущений через відсутнє обов'язкове значення, усе одно зсуває «поточну»
    погоду: його метеоумови враховуються, щоб наступні записи не взяли застарілу
    (сам рядок не підтягується);
  - логіка — `plan.carry` у `planImport` і `importRows(plan, { carryWeather })`
    (`src/dashboard-module-source-core.js`); поля метеоумов беруться з груп форми
    (`fieldSections`, група `inherit`), тож шаблони без таких полів не зачеплено;
    `plan.rows` лишається таблицею «як є», а протягнуті набори складаються лише в
    `importRows` (галочка вимкнена — записи без змін);
  - у форму запису цього не змінює: нові записи, як і раніше, беруть погоду з
    останнього запису модуля (`inheritedValues`).
- **Тести.** JS: `tests/dashboard-module-source.test.mjs` — 40 (заголовки, колізії
  й повне зіставлення всіх шаблонів Rust через `tests/helpers/rust-catalog.mjs`,
  колонки власника, метеоумови, вибір рядка заголовків, оцінка аркушів, значення,
  пропуски, попередження, зауваження правил форми, ліміт, форма запису, підписи й
  відмінювання, протягування метеоумов: та сама зміна, нове значення, неповний набір,
  без номера зміни, нова зміна, нерозібрана клітинка, погана погода, пропущений рядок,
  шаблон без метеоумов, підписи); `tests/dashboard-module-catalog.test.mjs` +4
  (`rowRuleProblem`, команди й відсутність запису в XLSX, розташування блоку,
  галочка протягування). Rust: 6 тестів
  читача (`module_source`) і 4 нові в `dashboard_modules` (записи в порядку, порожні
  `rows` = створення без записів, некоректний запис скасовує створення, понад
  10 000). Chromium-сценарії на синтетичній книзі й імітації бекенда (поза
  репозиторієм): 13 перевірок — таблиця профілю з трьома аркушами (заголовки в 3-му
  рядку), вибір аркуша, часткова схожість, порожній модуль без галочки, вибір
  файла (у тому числі скасований), помилка читання, таблиця без схожих аркушів,
  протягування метеоумов (два записи тієї ж зміни беруть погоду з попереднього,
  запис нової зміни без погоди лишається порожнім, галочка вимкнена — записи як у
  таблиці, неактивна без головної), вузький екран, світла тема, відсутність
  помилок консолі й системних діалогів.
- Припущення, які варто підтвердити: порядок трьох колонок «Вправа» — КБП → №1 →
  №2; «Так» у «ПМУ/СМУ» означає СМУ; кілограми палива назад у літри не
  перераховуються; метеоумови однією клітинкою — рівно чотири числа в порядку
  хмарність, НМХ, ВМХ, видимість; **метеоумови протягуються на записи тієї ж льотної зміни
  за номером зміни** (див. вище); якщо в таблиці номера зміни немає або він
  порожній (наприклад, об'єднана комірка «Льотна зміна» на кілька рядків), погода
  не протягується й блок про це попереджає — чи вважати порожній номер продовженням
  попередньої зміни, вирішує власник; імпорт одноразовий — пізніші зміни в XLSX
  модуль не підхоплює.
- Не перевірено: справжній файл власника (формати клітинок, об'єднані комірки,
  одна клітинка метеоумов, приховані рядки й стовпці); XLSX, відкритий у Excel
  під час читання; macOS і Windows; справжнє вікно Tauri й системне вікно вибору
  файла; поведінка `<dialog>` і `color-mix` у WKWebView та WebView2.

## Сторінка журналу: пошук, групи колонок, щільність (2026-10-19, гілка `claude/dashboard-modules`)

Рішення власника: з прототипу J3 (`docs/design/j3-dashboard-flow-prototype/`, перенесено
окремим комітом) інтегрувати послідовно сторінку журналу й екран «Перевірка»; правка
запису лишається в одному рядку, бічної панелі прототипу немає; схема БД для цієї
частини не змінюється.

- Ядро (`dashboard-module-catalog-core.js`): `tableColumnGroups` (Усі, Основне, Політ і
  наліт, Метеоумови, Екіпаж, Паливо й вантаж, Оцінки; кожне поле рівно в одній групі,
  невідомі — в «Основне»; менше двох груп — фільтра немає), `visibleColumnKeys` (тип і
  номер ПС видно в кожній групі), `rowMatchesQuery` (кожне слово запиту в показаному
  або сирому значенні, без регістру), `normalizeDensity`.
- Сторінка: панель над таблицею, коли є записи; колонки ховаються атрибутом `hidden`,
  `colgroup` і мінімальна ширина таблиці перераховуються; «№» — номер запису.
  «Редагувати» / «+ Додати рядок» повертають групу «Усі», пошук і групи на час правки
  вимкнено; `Esc` у пошуку очищає запит. Запит і група живуть у `state.tableViews` (до
  перезавантаження), щільність — у `localStorage` (`easywar.moduleTable.density`, з
  `try/catch`).
- Відмінність від прототипу: групи «СМУ, час у хмарах, під шторкою» віднесено до
  «Політ і наліт», а не до метеоумов (рішення власника: СМУ — ознака польоту);
  перемикача «Колонки N» немає — його роль виконують групи.
- Тести: +5 у `tests/dashboard-module-catalog.test.mjs`; сценарій Chromium (поза
  репозиторієм) — 10 перевірок: панель, пошук «тестенко мі-8», `Esc`, «нічого не
  знайдено», група «Метеоумови», компактна висота, правка в групі, збереження з
  пошуком, пам'ять щільності, вузький екран, світла тема.

## Екран «Перевірка»: виправлення значень до підтягування (2026-10-19, гілка `claude/dashboard-modules`)

Рішення власника: виправлення проблемного значення до імпорту; сире значення
лишається незмінним, виправлення зберігається окремо й видно користувачу; постійна
таблиця — міграцією `0011` з тестом застосування; не через динамічні колонки
`dashboard_data_*`.

- **База.** `0011_dashboard_module_corrections.sql` — таблиця
  `dashboard_module_corrections`: модуль, `row_id` запису, поле, сирий текст
  клітинки, введений текст (не порожній), причина, назва файла (без шляху), аркуш,
  рядок, заголовок колонки, час; одне виправлення на поле запису; каскад із модулем
  (а отже з профілем). Запис у `dashboard_data_<id>` містить виправлене значення.
  Лічильники міграцій 10 → 11 у `database`, `migration_startup`, `restore`.
- **Rust.** `create_with_import` (нове; `create_with_rows` делегує без виправлень)
  перевіряє виправлення (`validate_corrections`: є запис і поле, у записі є
  значення, текст у межах, без повторів) і пише їх тією самою транзакцією за
  `row_id`, які повертає `insert_rows`; помилка скасовує все створення.
  `get_data` віддає `corrections`; `replace_rows` видаляє виправлення записів, яких
  більше немає. Команда `create_dashboard_module` приймає необов'язковий
  `corrections`. Capabilities, CSP і залежності не змінено.
- **JS-ядро** (`dashboard-module-source-core.js`). `planImport` збирає
  `timeline` (рядки з даними по порядку, зокрема пропущені через обов'язкове
  поле) і `issues` (не розібрано / запис пропущено / правило форми; рядок, колонка,
  сирий текст, `prefill` — чи сирий текст є клітинкою саме цього поля).
  `buildImport(fields, plan, corrections)` накладає виправлення на копії записів,
  повертає пропущений запис, щойно обов'язкове поле виправлено, і заново протягує
  погоду; `plan.rows` не змінюється. `correctionOutcome` читає введений текст тими
  самими правилами, що й клітинку; `reviewState` — стан кожного зауваження;
  `correctionRecords` — виправлення для Rust (клітинка метеоумов дає запис на
  кожне поле погоди).
- **Інтерфейс.** Блок «Дані з вашої таблиці» — «Зауважень до значень: N» і
  «Перевірити й виправити…»; екран «Перевірка» (у тому самому вікні, `Esc` і «←
  До створення» повертають форму без втрат): картки з сирим текстом, полем,
  «Застосувати» / «Скасувати виправлення», швидкий вибір «0,3 км / 0,3 м»,
  лічильники; не більше 200 карток за раз. Після створення — розділ «Виправлено під
  час підтягування з таблиці» на сторінці модуля й позначка ✎ у клітинках.
- **Відмінності від прототипу.** Немає «Зберегти звіт перевірки» (це запис файла —
  потребує окремого рішення), немає «Не імпортувати рядок» (пропущений запис і так
  не підтягується, доки його не виправлено), кроків-«степера» немає — екран
  відкривається з блоку.
- **Тести.** Rust: 3 у `dashboard_modules` (збереження окремо від записів, невідповідне
